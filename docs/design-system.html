1. Status and authority

Written: 2026-09-05. Last amended: 2026-09-06.
Consolidates: docs/handoff/ (2026-09-05) — the IdeaScape desktop UI bundle, 12 screens.
Fidelity: high. Colours, type sizes, spacing, radii, shadows and copy are final.
Design system: Broadsheet, bound at docs/handoff/_ds/broadsheet-ceab0636-4e8c-4494-8c93-3524fad568e6/.

The authority rules

  1. This document wins over the handoff bundle. Where a mockup, the bundle README and this document disagree on anything visual, this document is correct.
  2. The plan wins over this document on scope, data model and architecture. The bundle README states this rule itself. docs/mvp-plan.html owns what gets built. docs/architecture.html owns how it is built. This document owns what it looks like and how it behaves on screen.
  3. docs/ wins over docs/handoff/plan/. The copies in the bundle's plan/ folder are a frozen historical record of what the designer worked against. They are never edited and never treated as current. (On 2026-09-05 they were byte-identical to the live docs.)
  4. A locked decision is never deleted. It is superseded, dated, with its reason, in the handoff log in section 2.

Two things the mockups are not

  • Card heights are content-driven. Where a card has no authored height it is as tall as its text. The prototype's absolute top/left values are illustrative placements. Real placements come from the placement table.
  • The 1180 × 720 frame is a mock viewport, not a window size. The real window is resizable. The left column, the properties panel and the title bar are fixed width. The canvas takes the remainder.

3. Base system and deliberate deviations

The base system is Broadsheet — "newsprint set for the web". Its own guide is at docs/handoff/_ds/broadsheet-…/readme.md. Its tokens are at …/styles.css, which is the authority on every colour value.

Broadsheet is an editorial system. IdeaScape is desktop application chrome. Seven of Broadsheet's rules are broken on purpose. This list is closed. Keep all seven. Add none. An eighth deviation is a design decision, not an implementation shortcut, and belongs in the handoff log first.

#Broadsheet ruleWhat IdeaScape doesWhy
1"Use Phosphor icons, in the duotone weight throughout." Phosphor regular weight throughout. Interface chrome runs at 12–16px. Duotone's second tone muddies at those sizes.
2"Do not structure the page with rules, borders or boxes." Reserve .card for discrete items only. Borders and boxes structure everything: a 34px title bar with a bottom border, a 168px left column with a right border, a 177px properties panel with a left border, and a surface-filled boxed card for every item on the canvas. Application chrome needs region separation that whitespace cannot carry. A canvas card is a discrete item, so that use stays inside the rule; the chrome borders do not.
3Radius scale is --radius-sm 1px, --radius-md 2px, --radius-lg 4px. "Never hard-code a px value the tokens already carry." Adds 3px as the dominant radius — cards, menus, panels and most buttons. 2px reads as square at card size; 4px reads as soft. 3px is the app's own step. Add it as a project token (section 5.2).
4Spacing scale 5 / 10 / 15 / 20 / 30 / 40px at density 1.25×. "Do not tighten the airy spacing scale." A tighter, finer scale: 2, 5, 6, 7, 9, 10, 12, 13, 14, 16, 22, 26, 34, 36, 44, 64px. Desktop tool density. Broadsheet's scale is set for an editorial page with one reading column, not for a 168px rail holding eleven rows.
5"This system shows no dark surfaces." A full dark theme, adding six values that are not in the token sheet: #1a1817, #262322, #302d2b, #3b3735, #ece9e6, #151312. A canvas app is used for long sessions. The six values are extracted for this design and must be added as project tokens (section 4.5).
6"Do not use both accents in the same small component." The properties panel footer holds an accent-bordered Duplicate button and an accent-2 Delete button in one space-between row. Destructive must read as destructive, and it must sit beside its opposite so the pair is scannable. This is the only place both accents meet.
7"For elevation use --shadow-sm/md/lg rather than ad-hoc box-shadows." Seven named shadows, six of them ad-hoc (section 5.3). Only the zoom bar's 0 3px 10px rgba(45,43,43,.16) is exactly --shadow-md. The app has distinct elevations for card, selected card, picker card, zoom bar, menu, popover and toggle knob. Broadsheet ships three steps. Add the rest as project tokens.
Reverted, not deviated. An eighth deviation — a sans-serif chrome font — appeared in every mockup frame (Verdana, Geneva, sans-serif). It was reverted on 2026-09-05: the chrome font is Broadsheet's Source Serif 4. See section 6 and the handoff log.

Two rules to carry into the implementation.

4.6 Accent text at paragraph sizes

Broadsheet tunes the accent-to-ground pair to at least 3:1. That is enough for icons, large text and interface chrome — not for body copy. The rule:

  • On the light ground, accent text at paragraph size uses --color-accent-700 #006786, never --color-accent.
  • On the dark ground the accent is already --color-accent-400 #62c5ee, a light step on a dark ground, which carries paragraph text.
  • --color-accent itself is for fills, outlines, borders and icons only.

Rules that matter:

  1. Endpoints sit on the card's real edge, not on an assumed one. Derive them from the placement rectangle, so a card that grows never leaves a line sprouting from its middle. (The prototype hand-computed these and had to correct them twice.)
  2. Direction comes from the arrowhead. orient="auto-start-reverse" lets one marker serve either end.
  3. Labels are HTML chips, not SVG text, so they can sit on an opaque ground. A chip must clear both cards and anything drawn above it. An open menu will occlude one — that is correct behaviour, but allow for it.
  4. Below 50px of line length, the chip is not drawn. Set by the owner, 2026-09-06. Measure the straight distance between the two endpoints — on an elbow route, the length of the longest segment, which is the only one the chip can sit on. Under 50px there is no room for a 10px chip with 1px 5px padding without covering both cards. The label is not lost — it stays on the connection, it shows in the properties panel when the connection is selected, and it reappears the moment the cards move apart or the canvas zooms in. Do not truncate, do not shrink the chip, and do not offset it off the line: hide it, and bring it back unchanged. 50px is the same threshold as the minimum card size (9.3).
  5. Lines are neutral ink, never the accent. The accent means "selected".
  6. A connection joins two placements on one canvas. Placing the same item on another canvas brings no lines with it.
  7. A connection carries a route — straight or elbow — the same way it carries a colour, a width and a direction. It is a property of the one connection, never an application-wide setting. Set by the owner, 2026-09-07. Reason: a diagram normally mixes the two, and an app-wide switch would restyle every line on every canvas at once. New connections start on straight, so no existing canvas changes shape.
  8. A line's shape is derived until the user says otherwise. A line with no anchor and no bend is computed from the two rectangles alone, and every line starts that way — which is what keeps contract 1 in section 10 true of the default. Twice narrowed by the owner, 2026-09-07: the rule first said the whole route was computed, then that only a bend was. Both ENDS can now be pinned to a card side (see Anchor) and the MIDDLE can be bent by hand (see Bend), because "which side does this come out of" and "go round that way" are diagramming decisions the application cannot read off two rectangles. What is authored is held relative to the cards, never as a canvas coordinate, so moving a card still re-forms the line rather than breaking it. Still a non-goal: more than one bend per line.
  9. An elbow does not go around cards. It may cross one. Obstacle avoidance is a deliberate non-goal — it is per-line path finding that has to re-run on every drag, and it is the wrong thing to put in front of the 60 fps / 250 card gate. The seam is left open: the geometry returns a list of points, so a future route can add points without touching the stroke, the hit path, the chip or the cull.

Storage, and why it is not a coordinate. One new column, bend, text, default empty, holding {"a":…,"b":…}. The pair is a position in the frame of the two card centres: a runs along the line from one centre to the other, 0 at one end and 1 at the other, and b runs at a right angle to it in the same units as that distance. So a bend slides, stretches and turns with its two cards — move a card and the shape the user drew is kept, which is the whole reason for the frame. The frame is the two centres and not the two endpoints on purpose: an endpoint depends on where the line is going, and the bend is what decides that, so measuring against endpoints would be circular. An unreadable value draws as a plain line rather than failing the overlay. This is an amendment to the data model in docs/mvp-plan.html §4 and docs/prd.html §4.

What a drag may do depends on the route, and the geometry decides it — not the handle. The same stored bend is read differently by the two routes, and each one reports back where its handle goes and the one direction it may travel.

  • Straight. The handle IS the bend, and it moves at a right angle to the line: drag the middle of a horizontal line and it moves up and down, and sideways travel is ignored. Where along the line the bend sits is fixed when the press lands — the stored bend's own place, or the midpoint the ghost handle sits on — so the handle never jumps as a gesture starts. Sliding it along its own line changes no shape worth having, and it walks the handle off the drawn line: a bend dragged out past a card sends the route back across that card to reach it.
  • Elbow. The handle sits in the middle of the crossing — the middle run, the only one whose position nothing but taste decides — and slides on that run's own single axis, carrying the whole run with it. The route keeps its three runs and gains no corner. The geometry reads only that one axis off the bend, so the other half of the stored pair is simply not consulted while the line is an elbow.

The bend is kept off both cards. It is held 8px clear of either card's border, and it is pushed out of one it has landed inside — by a drag, or by a card later being moved over it. A bend under a card is a bend the line cannot show: the route is clipped at the border, so the drawn line stops there while the bend, and the handle on it, sit under the card with nothing reaching them. The route and the handle read the same pushed-out point, so the handle is always ON the drawn line and the two can never disagree.

The handle. 7 × 7 like the endpoint handles and on the same rung above the cards, but hollow — --color-surface fill, 1.5px --color-accent border, 1px radius — so it never reads as an endpoint. It is the same language a card's resize handle uses. On a line with no bend it sits on the midpoint of the route's longest segment — the same segment the label chip uses, the only one with room — and is drawn at .55 opacity: at that point it is an invitation, not a state. It goes to full strength once the line is bent. The transparent grab target is 14 × 14, as it is on an endpoint.

Straightening. A drag can only place a bend, never remove one. Two things remove it: Enter or Space on the focused middle handle, and a new Bend group in the properties panel, sitting between Anchor and Color, which reads One hand-placed bend or No bend in 11px at .45 opacity and carries one full-width Straighten Line button, disabled while there is no bend.

Entry points: the Connect tool in the left column, or Connect from here (ph-flow-arrow, shortcut C) in a card's context menu.

10. Cross-cutting interaction contracts

These hold on every screen. They are numbered so a phase doc or a review can cite them.

  1. The application never moves a card and never chooses a position. New cards land at the pointer. Placement is free. This rules out any automatic layout.
  2. A card exists before the network is consulted. Pasting an address creates the card immediately, marked not fetched. The wait never blocks the work.
  3. A failure is drawn on the card, never in a dialog. All six failure states in section 15.2 are normal UI in the visual language of this document.
  4. Every fetch is cut off at 5 seconds and treated as a failure.
  5. There is no Save button and no manual save mode. The title bar's save state is the only affordance.
  6. Settings apply as they are made. No Save, no Cancel, no confirm.
  7. Every edit is undoable. Undo and redo hold the current session only and clear when the project closes. The properties panel footer says so on every screen that shows it.
  8. Nothing auto-commits a destructive act. Delete is reachable from the panel footer and from the element menu, and both are undoable. No timed deletion. No silent cleanup the user can see happening.
  9. The accent means "selected" or "active", and nothing else. Connection lines, dividers and card chrome never take it.
  10. The second accent means "destructive", and nothing else. It appears in exactly two places: the panel's Delete button and destructive menu rows.
  11. No route is the only route. Every action in a context menu is also reachable from the left column or the properties panel.
  12. Canvas names always rank above cards in search. A requirement, not a preference — it is the direct answer to the loudest complaint in the competitive scan.
  13. The properties panel collapses whenever the selection is empty, including during a search.
  14. Only the view position and zoom persist per canvas (view_x, view_y, view_zoom). Selection, active tool and search state do not.

12. Accessibility

  1. The accent pair is tuned to 3:1, not 4.5:1. That is enough for icons, large text and interface chrome. For accent text at paragraph size use --color-accent-700 on light. Never --color-accent.
  2. The opacity ladder is the main contrast risk. Twelve roles sit at .5 or below and four sit at .4 or below. --color-text at .35 on --color-surface will not reach 4.5:1. Those roles are disabled states and decorative hints, which is defensible — but the .42 panel footer, the .4 empty-state hint and the .38 vertical label carry real information. Measure all three before sign-off.
  3. Keyboard focus is a 2px accent ring with a 2px offset, on every interactive element. Never the browser default.
  4. Every action has a keyboard route. The map in 11.6 is the contract.
  5. Image cards carry alt text, edited in the panel's Alt text group. It is a real alt value, not a tooltip.
  6. Icon-only buttons need an accessible name. Thirteen controls are icon-only: the three window controls, the zoom bar's four, the panel's Duplicate, Delete, Front, Back and "Show in folder", and the collapsed-panel caret. Give each one a label. "Show in folder" already has a title; the rest do not.
  7. Colour is never the only signal. The active tool row carries weight 600 plus a fill. The active canvas row carries weight 600 plus a fill. Disabled rows carry opacity plus a disabled attribute.
  8. Rendered Markdown is cleaned before it goes into the page. A note card can never run script. Fetched Open Graph values are plain text and are never inserted as markup. (From docs/architecture.html §8.)
  9. The dark theme is a real theme, not a filter. It carries its own contrast obligations. --color-accent-2-400 #ff90b1 on #262322 is unmeasured — see open question 6.
