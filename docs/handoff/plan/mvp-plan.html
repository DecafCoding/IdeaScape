IdeaScape — MVP Plan

A desktop canvas application. You place small ideas on a canvas and connect them to build a larger concept.

Status: scope agreed. Ready for dev-architecture.
Written: 2026-09-05, from the initial requirements interview.
Companion research: docs/competitive-scan.html (10 comparable applications).
Technical authority: docs/architecture.html.
Visual authority: docs/design-system.html — every colour, size, spacing, screen layout and on-screen state. This document does not restate them.
This document is the scope authority. Downstream skills read it at this fixed path.

1. Problem and users

The user

One person. The author of this plan. The application runs on their own machine.

There are no user accounts. There is no sharing. There is no team. This is settled and it is on the "never" list in section 3.

The problem

The user gathers raw pieces of an idea. Those pieces are notes, pictures, web links and videos. The pieces sit in different places today. Some are in a browser bookmark list. Some are in a notes application. Some are in a folder of pictures.

Nothing holds the relationship between the pieces. The user cannot see how one piece supports another. The bigger concept stays in the user's head.

What "solved" looks like

The user opens one canvas. Every piece of one idea is on it. The lines between the pieces show how the idea holds together. The user can look at the canvas and see the concept, not just the parts.

Two example projects the user named

  • Research. Collect pictures, notes and web pages about building a generation spaceship. Pieces are mostly used once.
  • Story building. One project for a story. One canvas per chapter. Characters, tropes and themes get reused across chapters. This drives the data model in section 4.

What this is not

This is not a moodboard tool for collecting references. Collecting is supported. The purpose is to develop a concept. Connections carry meaning.

2. Core loop

The user repeats this all day. Everything else in the application supports it.

  1. Add a card anywhere on the canvas.
  2. Drag it to where it belongs.
  3. Draw a line from it to another card.

Placement is free. The application never moves a card for the user. The application never creates a card in a position it chose. The user owns the layout.

This rules out an automatic mind-map layout, where a new card appears already attached to its parent. That shape is on the backlog as a shortcut, not as the core loop.

3. Scope

In the MVP

  • Pan and zoom canvas, with free placement
  • Note cards, with plain text and basic formatting
  • Image cards, by file drop, file picker and clipboard paste
  • Web link cards, showing title, icon and preview picture
  • Video cards, showing title and thumbnail, opening in the browser on click. YouTube only
  • Connections between two cards on one canvas, with arrow direction and an optional text label
  • Move, resize, multi-select, delete and z-order for cards
  • Automatic save after every change
  • Undo and redo, for the current session
  • Projects, each holding many canvases
  • A flat list of canvases inside a project, with create, rename and delete
  • Text search over canvas names and card text, with canvas names ranked first
  • Works with no internet, except for link previews and video thumbnails
  • Duplicate a card, from the element menu and from the properties panel
  • A keyboard shortcut set — the 14 keys printed on the context menus and the search footer. See docs/design-system.html §11.6
  • A Settings screen, applied as changes are made, holding: the project folder (read-only), auto-save cadence, snap to grid, zoom with, theme, and — from P6 — show writing cards
  • A light and a dark theme, chosen as Light, Dark or System
  • The writing pack — seven typed card types built from data blueprints, connections that carry a role, list fields with chips on the card face, and a card that expands into its own canvas. Builds in P6. See docs/feature-writing-pack.html

  • Relationships between library items, and a graph view of them
  • A browser extension web clipper
  • AI features, started by the user, using the user's own key
  • Freehand drawing and an ink layer
  • Book templates — pick a genre and a sub-genre, then fill a Book card's fields from a guide drawn from a previous book. Deferred inside the writing pack, with its rulings already recorded. See docs/feature-writing-pack.html §3
  • Highlight mode — click a chip and every card carrying that value lights up. Deferred inside the writing pack
  • Board cards — a card whose content is computed rather than typed. Deferred inside the writing pack
  • User-written blueprints — a screen where the user builds their own card type. Deferred inside the writing pack
  • Version history and restore
  • PDF cards and PDF annotation

  • Task lists and column layouts

  • Import from other tools
  • A mobile application
  • Operating systems other than Windows
  • A one-time licence key check, for a paid download. This is checked offline. It is not billing

Never

These are ruled out permanently. They leave the backlog. They are not offered again.

  • User accounts and sign-in
  • In-application billing and subscriptions
  • Collaboration, including real-time shared editing, comments and share links
  • Cloud storage of the user's project data
  • Usage tracking, analytics and any call the user did not start

If the application is ever sold, it is sold as a download with a one-time key. The key is checked offline. That does not reopen accounts or billing.

4. Data model

Shape

Project
 ├── Canvas          (many per project)
 │    ├── Placement  (many per canvas) ──► Item
 │    └── Connection (many per canvas) ──► two Placements
 └── Item            (the project library; many per project)

The key decision: a card is a placement, not the content

A card on a canvas holds position and size. It points at an item. The item holds the content. The item lives in the project library.

Most items have exactly one placement. That is a picture used once. It feels simple and the user never thinks about the library.

A reused item has two or more placements. That is a character in a story, shown on three chapter canvases. It is the same record and the same code path.

This costs one extra table now. Without it, adding reusable characters later would need a rewrite of the data model, and that rewrite would take every existing canvas with it.

Entities

EntityFieldsNotes
project id, name, created_at, updated_at One project is one folder on disk. See section 6
canvas id, project_id, name, sort_order, view_x, view_y, view_zoom, created_at, updated_at The view fields remember where the user was looking
item id, project_id, kind, payload, created_at, updated_at kind is note, image, link or video. payload is typed per kind
placement id, canvas_id, item_id, x, y, width, height, z_order One card on one canvas
connection id, canvas_id, from_placement_id, to_placement_id, label, directed, color, width, label_visible, route, from_anchor, to_anchor, bend Joins two placements on the same canvas. color, width, label_visible, route, from_anchor and to_anchor are style keys resolved by the front end; route is straight or elbow, and each anchor is auto or a card side. bend is a hand-placed bend as JSON, held in the frame of the two card centres, or empty for none. No canvas coordinate is ever stored on a connection. See docs/design-system.html §9.13

Item payload, by kind

note   { title, text }
image  { asset, natural_width, natural_height, alt }
link   { url, title, description, favicon_asset, thumbnail_asset, fetched_at }
video  { url, provider, title, thumbnail_asset, fetched_at }
blueprint { blueprint, name, detail_canvas_id, fields }

An asset value is a file name inside the project's assets folder. It is never an absolute path.

A note carries a title as well as its body text. The title is a plain string, not Markdown. It is what the card shows at the top, and what a search result names. Both fields are searched. Added 2026-09-05 by dev-ui-update: every note card in the design handoff has a title, and the earlier payload had nowhere to put it.

The kind field with a typed payload is what lets a fifth kind be added cheaply. A character kind later brings its own payload and its own editor. Behaviour stays per kind.

Added 2026-09-07 by dev-add-feature: the fifth kind is blueprint, and it is the only kind the writing pack adds. The card type — Book, Chapter, Scene, Beat, Character, Location — is a value inside the payload, not a value of kind. SQLite cannot change a CHECK constraint in place, so a kind per card type would mean rebuilding the item table for every new card type. With the type in the payload, a new card type is a data file and no migration at all. The cost is that kind no longer says what a card looks like; code reads payload.blueprint. See docs/feature-writing-pack.html §5.

Connections join placements, not items

A line lives on one canvas. Placing the same item on a second canvas brings no lines with it. What the user sees is what the user drew.

Relationships between items are a different idea. They are deferred. They arrive with the graph view.

Ownership and lifecycle

  • Deleting a project deletes its folder, which holds the database and every asset file.
  • Deleting a canvas deletes its placements and its connections. Items are then checked, and the rule below applies.
  • Deleting a placement deletes the connections attached to it.
  • Deleting the last placement of a note, image, link or video item deletes the item and its asset files.
  • Deleting the last placement of a blueprint item keeps the item. It moves to the Unplaced list in the left column, where it can be placed again or deleted for good.

The rule stops invisible junk. The MVP has no library screen, so an item with no placement could never be seen or removed. Undo restores the item, the placement and the asset files together.

2026-09-07 — the delete rule is corrected by dev-add-feature. It was one rule for every kind: deleting the last placement deleted the item. A blueprint card is meant to be reused, so that rule would destroy a Character when the user removed them from the one chapter they appear in, taking their sliders, tropes and notes with them. The four original kinds keep the old behaviour exactly. Blueprint items survive, and the new Unplaced list keeps the old rule's promise that nothing becomes invisible. See docs/feature-writing-pack.html §5.

5. Interfaces

Surface

One desktop application window on Windows. It is installed. It runs with no internet.

There is no command line, no web page and no public interface for other programs.

Screens

Every screen below is drawn and measured in docs/design-system.html §9. That document is the visual authority; the table here names only what each screen is for.

ScreenPurpose
Project pickerOpen a project folder. Create a new one
Canvas viewThe main screen. This is where the core loop happens
Empty canvasThe state right after a new project. It says how to add the first card
Left columnA fixed panel beside the canvas. It holds the canvas list, search, the tools, the add and history actions, and Settings
Properties panelA fixed panel on the other side. It edits the selected card: position, size, per-kind fields, z-order, duplicate and delete. It collapses when nothing is selected
SearchA box in the left column. It opens results over the canvas. Results name canvases first, then cards
SettingsA full page replacing the canvas. Changes apply as they are made. There is no Save and no Cancel

The left column is the name used in every document. It was called the "canvas list" before 2026-09-05, and the design handoff also calls it "the rail". Use left column.

Inputs

  • Mouse. Drag to move. Handles to resize. Drag on empty space to select many.
  • Keyboard. The full shortcut set is in docs/design-system.html §11.6 — 14 keys, each of them printed on a context menu or the search footer, so the application must honour them. In short: N note, I image, C connect, Enter edit or open, Esc clear or close, Del delete, ↑ ↓ move through results, and Ctrl + D C V A 0 ] [. Undo and redo use the Windows convention, Ctrl+Z and Ctrl+Y.
  • File drop from Windows Explorer, for pictures.
  • Clipboard paste, for pictures, plain text and web addresses. A pasted address becomes a link card or a video card, chosen by the address.

Outputs

None in the MVP. Export is deferred. The user's data is still theirs, because the project folder holds a readable database and the original picture files.

6. Architecture

Runtime

PartChoiceReason
Desktop shellTauri Uses the browser engine already in Windows. The download is about 10 MB, against about 150 MB for Electron. Lower memory use helps the speed target
BackendRust, inside Tauri It comes with the shell. It owns the database and the files
InterfaceWeb technology in the Tauri window Web link previews and rich text need a browser engine. A native application would have to embed one anyway
StorageSQLite, one file per project No server. Fast search. Small safe writes for automatic save

Drawing the canvas

Each card is a real element in the page. The canvas moves and scales with a transform.

Only the cards inside the view window are drawn. A card outside the view is removed from the page. This is called culling.

Obsidian Canvas is slow because it draws every card all the time, even far off screen. Culling is the direct answer to that. tldraw and Kinopio both use this approach and both stay smooth.

Drawing everything with WebGL was considered and rejected. Text editing and rich content cannot be drawn that way, so page elements would be needed on top regardless.

Project folder on disk

MyProject/
  ideascape.db      SQLite. Canvases, items, placements, connections
  assets/           Every picture file, copied in, named by content hash

Pictures are copied into the folder. They are never referenced where the user left them. This makes the folder self-contained, so it can be moved, zipped or backed up. It also stops the card breaking when the user moves or renames the original file.

External dependencies

  • Microsoft Edge WebView2, for the browser engine. It ships with Windows 11.
  • Web page fetching, for link preview title, description and picture.
  • YouTube public metadata, for the video card title and thumbnail. Vimeo was removed on 2026-09-06 — see the deferred list in section 3.

Deployment

A Windows installer. No server. No update service.

7. State and failure

Saving

  • Every change is written to SQLite. Rapid changes, such as dragging a card, are grouped and written when the drag ends.
  • A change that touches several rows is written in one transaction. A crash part-way leaves no half-finished state.
  • Closing the application saves the current view position and zoom for each canvas.

Undo

  • Undo and redo hold the current session only. Closing the project clears them.
  • Undo restores deleted items, placements, connections and asset files together.
  • Persistent history is deferred. It arrives with version history.

Failure

FailureBehaviour
No internet when a link is pasted The card is created at once, showing the address. It is marked as not fetched. A retry button is shown
A web page will not load or has no preview data The card keeps the address and the page title if there is one. No preview picture. This is a normal state, not an error dialog
A preview fetch is slow It is cut off after 5 seconds and treated as a failed fetch
An asset file is missing from the folder The card shows a clear missing-file marker. The application does not crash and does not delete the item
The database file is locked or damaged The project does not open. A plain message names the file. No other project is affected
The application is force-closed while editing Everything is kept except the action in progress

There is no concurrency problem to solve. One user, one machine, one open project at a time.

10. Done criteria

The MVP is finished when every line below passes.

  • Make a project. Make 3 canvases inside it
  • Put 250 mixed cards on one canvas. Panning holds 60 frames per second
  • That project opens in under 2 seconds
  • Paste a web address. A preview card fills in within 3 seconds, or shows a clear failure card with a retry button
  • Paste a YouTube address. The card shows the video title and thumbnail. Clicking it opens the video in the browser
  • Join cards with arrows. Put a label on an arrow
  • Close the application. Open it again. Everything is exactly as it was left, including the view position
  • Search a canvas name. That canvas is the first result
  • Force-close the application while editing. Nothing is lost except the action in progress
  • Delete the last card of an item. The item and its picture file are gone from the folder. Undo brings both back
  • Set the theme to Dark. Every screen renders correctly. Nothing moves between the two themes
  • Every screen matches docs/design-system.html at its locked token values, in light and in dark

11. Open risks and assumptions

Table stakes the MVP does not fully meet

Both gaps below were raised in the interview and accepted on purpose. The stated reason was to prove the rest of the application first, then add them.

  • Export. Every comparable application offers some export. Lock-in is a market-wide complaint. IdeaScape has no export button in the MVP. The data is still the user's, because the project folder holds a readable SQLite file and the original pictures. Moving to another tool would still be hard.
  • Video. Every comparable application plays video in place. IdeaScape shows a title, a thumbnail and a link. This is a visible gap next to Milanote.

Risks

RiskEffectAnswer
Culling does not reach 60 frames per second The main promise of the product fails It is the P1 gate. It is proved before any other work
Rust and Tauri are unfamiliar P1 takes longer than expected Most of the work is in the web layer. The Rust side only handles the database and files
WebView2 is missing on an older machine The application will not start The installer includes the WebView2 bootstrapper
Web pages block preview fetching, or give poor data Link cards look plain The failure states in section 7 are designed as normal states, not errors
YouTube changes its public metadata Video cards lose title and thumbnail The card falls back to the address. The card still works. Only one provider is supported, so there is one thing to fix
The library has no screen in the MVP Reusable items cannot be managed yet The delete rule in section 4 stops junk building up until the screen exists

Assumptions

  • The user works on one project at a time.
  • 250 cards on one canvas is enough. The scan shows other applications struggle at a few hundred, so this is already competitive.
  • Copying pictures into the project folder is acceptable disk use.
  • Windows 11 is the only target for the MVP.
