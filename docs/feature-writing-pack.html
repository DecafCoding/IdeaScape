IdeaScape — Feature Plan: The Writing Pack

Give IdeaScape a set of typed cards for writing a book. The card types are data, not code. Cards join with lines that carry a meaning. The outline is the canvas.

1. Summary and motivation

What is missing today

The MVP is finished. All five phases are complete. A user can place notes, pictures, links and videos on a canvas and join them with lines.

Every card is the same shape. A card holds free text. Nothing on the canvas knows what it is. A character and a chapter are stored identically, so the application cannot show a character differently, cannot offer a list of tropes, and cannot tell that four beats belong to one scene.

docs/mvp-plan.html §1 already names story building as one of the two example projects the user gave: "One project for a story. One canvas per chapter. Characters, tropes and themes get reused across chapters." The data model was built for that use. The card types were not.

What "done" changes

The user makes a canvas for a chapter. They add Beat cards and wire them into a Scene card. They add Character cards and wire those into the scene as well. They add a Chapter card and write the prose in it. They go to the book canvas, where the same Chapter card sits beside twenty-nine others.

Every card carries the fields its type needs. A Character has personality sliders. A Book has a genre, a sub-genre and its tropes, printed on the card face as chips. Nothing is required. A card with only a name is valid.

Why now

The MVP shipped. The plan's own deferred list holds four rows that are all one feature seen from four sides: reusable shaped items, templates, tags and metadata, and boards nested inside a canvas. Building them separately would build the same machinery four times.

The plan predicted this. docs/mvp-plan.html §4 says: "The kind field with a typed payload is what lets a fifth kind be added cheaply. A character kind later brings its own payload and its own editor." This feature is that sentence, built.

2. Fit with the existing application

It extends the core loop. It does not change it

The core loop is: add a card, drag it where it belongs, draw a line to another card. A blueprint card is added, dragged and joined exactly as a note card is. Nothing about the loop changes.

The plan's placement rule holds. The application never chooses a position for a card. It never moves a card for the user. That is why the template importer in section 3 fills fields and creates no cards.

It uses the data model as built

docs/mvp-plan.html §4 separates an item from a placement. The item holds the content. The placement holds position and size on one canvas. One item may have many placements.

That is what makes a Character usable on three chapter canvases as one record. It is also what makes a Chapter card appear both on its own chapter canvas and on the book canvas. There is no copy to keep in step. It is one card, placed twice.

It obeys the never list

  • No accounts, no sharing, no cloud. Nothing here touches them.
  • No network call the user did not start. This feature makes no network call at all. The list content is read from a local file that ships with the application.
  • No usage tracking. No update check.
  • No AI. See section 3.

3. Scope

In — P6

  • One new item kind, blueprint. The card type lives in the payload, not in the schema.
  • The blueprint engine. One form that reads a field list. Card types are data files, not code.
  • Seven field kinds: Short Text, Long Text, Pick, Pick Many, Image, Number, Scale.
  • Seven shipped card types: Book, Chapter, Scene, Beat, Character, Location, Theme-free Note stays as it is.
  • The combo control. A text box with a list button beside it. A typed value is always accepted. Used by Pick and Pick Many.
  • Shipped lists — genres, sub-genres, story tropes, character tropes, themes. Read-only. Drawn from the Book Guides library.
  • User list entries, held per project, so a copied project carries its own vocabulary.
  • One-hop list filtering. A field may name one parent field. The filter sorts the list. It never removes an entry.
  • Chips on the card face. A Pick or Pick Many value marked showOnFace prints as a chip.
  • Scale fields, with Randomize. The Character personality spread is five Big Five sliders, with the shaped roll carried from PlotReactor.
  • Connection roles. A new role column. Six suggested roles. Any card may join any card. No pair is ever refused.
  • Expand Into A Canvas. A card may point at a canvas that details it. Opening the card opens that canvas.
  • The delete rule, corrected. A blueprint item survives the deletion of its last placement. See section 5.
  • An Unplaced list in the left column, so a blueprint item with no placement is still reachable and still deletable.
  • Search reaches blueprint cards — the name field and every Long Text field.
  • A Settings toggle, Show Writing Cards, default on. It hides the seven card types from the Add menu. It never hides a card that is already on a canvas.

Deferred — real, wanted, not now

  • Book templates. Pick a genre, pick a sub-genre, pick a template drawn from a previous book, and have it fill the Book card's fields. This is the Guide Library from PlotReactor, ported. It is deferred because P6 must prove the card and field machinery first. Its rulings are recorded in section 5 so the later work cannot contradict this one.
  • Highlight mode. Click a trope chip and every card carrying it lights up while the rest dim. This is the strongest visual idea in the whole feature. It is deferred only because it needs the chips to exist first.
  • Board cards. A card whose content is computed, not typed — "Tropes In Play", a cast list, the chapter spine. It needs a second card concept and live refresh.
  • User-written blueprints. A screen where the user builds their own card type. The engine is the same. The hard parts are what happens to existing cards when a field is removed, blueprint versioning, and a broken blueprint file.
  • A Link To Card field. A field that points at another card. Connections already say this, and two ways to say one thing is a defect.
  • The full library screen. P6 ships an Unplaced list only. The complete library screen stays on the backlog.
  • Card packs. Turning sets of card types on and off. One flat writing pack ships. Splitting later is easy. Merging back is not.
  • AI filling a field. The blueprint's meaning line is the only seam. It earns its place in P6 as on-screen help text.

Never — not this product

  • A required intake form. No wizard. No interview. No field that blocks a save. A card with only a name is always valid.
  • A hard rule table for connections. The application never refuses to join two cards.
  • A filter that hides a list entry. Filtering sorts. A typed value always works.
  • Shipping the craft guide documents themselves. Carried from the PlotReactor ruling in section 5.
  • MBTI or Enneagram type pickers. A typed system does not belong on a slider.
  • AI-generated slider values. Randomize is local random numbers, permanently.

5. Data model changes

Ruling: one new item kind, not one per card type

item.kind gains exactly one value, blueprint. The card type is a field inside the payload.

blueprint {
  blueprint: "character",        // which card type this is
  name: "Untitled",              // every blueprint card has a name
  detail_canvas_id: 42 | null,   // Expand Into A Canvas
  fields: { <field key>: <value> }
}

SQLite cannot change a CHECK constraint in place, so widening CHECK (kind IN (...)) means rebuilding the item table. Doing that once is acceptable. Doing it for every new card type is not.

With the type in the payload, a new card type is a new data file and no migration at all. That is the whole point of blueprints, and it is also what keeps user-written blueprints possible later — a user cannot ship a migration.

The cost is stated plainly: kind no longer tells the front end what a card looks like. Code must read payload.blueprint. That is one extra step, in one place.

A blueprint is a read-only data file that ships inside the application. It is not a database row. A card refers to it by id.

Ruling: a pick entry is an id, your text and its sources

Carried unchanged from feature-guide-library.html. A Pick or Pick Many value is not a plain string.

{ id: "trope.chosen-one" | null,   // null when the user typed their own
  text: "...",                     // the user's own words. Theirs from then on
  sources: [ ... ] }               // where it came from. Read-only. May be empty

Editing your own text never changes the id. An id means "this came from there". It does not promise you used it the same way. A value the user invents has no id and is fully valid.

This buys the deferred template importer, the deferred highlight mode and any later count or check, with no new machinery. It costs one nested shape today.

Ruling: the last-placement delete rule is corrected

This is a change to an existing, shipped rule. docs/mvp-plan.html §4 says: "Deleting the last placement of an item deletes the item and its asset files." That rule was written because the MVP has no library screen, so an unplaced item would be invisible junk. A reusable Character breaks it. Removing a character from the one chapter they appear in would destroy the character record, its sliders, its tropes and its notes.

The corrected rule:

  • note, image, link and video keep the existing behaviour. Deleting the last placement deletes the item and its asset files. Nothing changes for them.
  • blueprint items survive. The item stays in the project with no placement.
  • An unplaced blueprint item appears in a new Unplaced list in the left column. From there it can be placed on a canvas or deleted for good.
  • Deleting an unplaced blueprint item deletes it and releases its asset references, in one transaction, undoable in one step.

The Unplaced list is the smallest thing that keeps the old rule's promise. Nothing becomes invisible junk. The full library screen stays deferred.

Connections gain a role

connection gains one nullable column, role. It is a short text value. It does not replace label, which stays a free note the user types.

Ruling: roles are loose. Any card may join any card. The application suggests a role from the two card types. The user may change it to anything, including Relates To. The application never refuses a connection and never shows a validation error. Beat straight to Chapter is a real way to write, and a rules table would be long, wrong and irritating.

Every existing connection has role = NULL, which reads as Relates To. No back-fill is needed.

Expand Into A Canvas

payload.detail_canvas_id points at the canvas that details this card. It is set when the user presses Expand Into A Canvas. That action creates a canvas, names it after the card, and places this same card on it.

Because a card is an item with many placements, the card on the book canvas and the card on the chapter canvas are one record. Editing either edits both. There is no copy and nothing to keep in step.

A cycle is allowed. Canvas A may hold a card whose detail canvas is B, while B holds a card whose detail canvas is A. Nothing is drawn inside anything, so nothing recurses. Deleting a canvas sets detail_canvas_id back to null on any card that pointed at it.

Personality, carried from PlotReactor

Carried unchanged from feature-character-record.html. It is a settled specification and this feature does not re-decide it.

  • Five Big Five sliders. Whole numbers, −3 to +3, seven notches. All 0 by default, and all 0 is a real answer meaning "unremarkable, like most people".
  • A plain word at each end of every slider. The words live in the blueprint.
  • One Randomize button on the section header. It rerolls all five and touches nothing else.
  • Each slider rolls on a bell-shaped table. The relative weights for −3, −2, −1, 0, +1, +2, +3 are 1, 3, 6, 8, 6, 3, 1.
  • The guarantee. If all five results fall inside −1 to +1, one slider chosen at random rerolls until it reaches −2, +2 or beyond.
  • Plain local random numbers. No network call. No AI. Permanently.
  • Undo restores all five previous values in one step.

The guarantee is the point. An unguarded bell curve gives a cast of ordinary people. A flat roll gives a cast of extremists. The guarantee gives a mostly ordinary person with one clear edge.

Rulings recorded for the deferred template importer

These are carried from feature-guide-library.html. Nothing in P6 implements them. They are written here so the later work cannot contradict this plan.

  • Generic fields only. A book guide records every element twice — as that book did it, and with the names stripped out. The application loads the stripped half only. The rule is enforced in the reader, not in the interface, so no later screen can leak a specific field by accident. Title, author and year are facts and are shown.
  • Copy, never reference. Applying a template copies the text into the project. Removing a guide afterwards changes nothing in any book. Its source lines grey out and wake on re-add.
  • One entry per id, many sources. Pulling the same trope from two guides adds a second source to the existing entry. It never creates a second entry.
  • Templates fill fields. They create no cards. One guide can carry 31 slots and four guides can offer over sixty rows. Dropping sixty cards on a canvas would also break the plan's rule that the application never chooses a position for a card.

7. Architecture fit

Outcome: it fits, with three narrow exceptions. No decision in docs/architecture.html has to change. No amendment is needed and none was made.

Exception 1 — search-method widens from three queries to four

The decision says three LIKE queries: canvas names, note titles, note bodies. This feature adds a fourth, over blueprint card names and Long Text fields, using SQLite's built-in json_extract as Phase 4 already does.

The ranking rule is unchanged and is the part that matters. Canvas names still rank first. The size argument still holds: 25 canvases times 250 cards is about 6,000 rows, and a full scan of 6,000 short rows takes a few milliseconds. This is a widening inside the decision, not a departure from it. Its undo cost stays cheap.

Exception 2 — settings-storage grows from five values to six

The decision says settings.json "holds the five values the Settings screen edits". This feature adds a sixth, show_writing_cards.

The decision itself is untouched. It is still one JSON file per machine, under %APPDATA%\IdeaScape, outside every project folder, written by the application, with working defaults, never required to exist. Nothing in it is user data. Its undo cost stays cheap. This is a sixth scalar in a file the application owns.

One stale line to correct later. docs/architecture.html §3 and CLAUDE.md both say settings.json holds five values. After P6 that is six. This feature plan does not edit either file — dev-architecture owns the first and dev-claud-md the second. Correct both when P6 is planned, not before.

Exception 3 — the item table is rebuilt once

storage-engine assumes additive migrations. Migration 0007 is not additive. It creates a new table, copies every row, drops the old one and recreates the indexes, because SQLite cannot change a CHECK constraint in place.

It is done once. Section 5 records why: putting the card type in the payload means no later card type ever needs a migration. If a second table rebuild is ever proposed for the same reason, that is a signal the payload design was wrong, and it should return to dev-architecture.

The one thing that was not settled — now settled

docs/design-system.html now holds this feature in full. §9.25–§9.33, folded in on 2026-09-08 from the revised handoff bundle: the generated blueprint form, all seven field controls, the combo in four states, the chip, the slider and its dice button, a card face for each of the seven card types, connection roles, and three full-screen sheets.

Its properties panel stays at 177 px expanded. The bundle drew every writing panel at 252 px; the owner declined that, so each control was re-measured for 153 px of content width. Only the Number field moved, and it moved by one pixel.

CLAUDE.md says: "Read it before writing any component. Do not invent a visual value." That still holds — and there is now something to read. P6 can be executed.

8. Compatibility and rollout

  • Existing projects. A project made in P1 to P5 opens in a P6 build with no change. The three migrations run when the project opens, as the existing rule already requires.
  • Existing cards. Note, image, link and video cards are untouched, on screen and in storage. Their delete rule is unchanged.
  • Existing connections. Every one gets role = NULL, which reads as Relates To. No back-fill.
  • Going backwards. A P6 project opened in a P5 build loses its blueprint cards, because that build's kind check rejects them. One way, and normal for a schema change.
  • No feature flag. One user, one machine, no staged rollout. A flag would be pure cost.
  • Nothing to fill in. No key, no service, no setting. The lists ship inside the application.
  • Intermediate states are valid. A blueprint card with only a name is a complete card. A canvas with no Chapter card is a valid canvas. Nothing blocks a save, ever.

9. Testing and regression plan

Proves this feature works

  • Migration 0007 runs on a project holding note, image, link and video items. Every row survives, both indexes exist, and every card still draws.
  • A blueprint card saves with every field empty except a default name. Nothing blocks the save.
  • Every one of the seven field kinds round-trips through the payload and back.
  • A typed value not in a shipped list is accepted, saved, and offered again in that project.
  • A filtered list sorts. Every entry is still reachable, including untagged ones.
  • All five Character sliders default to 0, and an all-zero spread is a valid saved state.
  • Randomize never leaves all five sliders inside −1 to +1. Run it 10,000 times and assert the guarantee holds every time.
  • The Randomize weight spread matches 1, 3, 6, 8, 6, 3, 1 within tolerance over a large sample, measured before the guarantee reroll.
  • Undo after Randomize restores all five values in one step, and Randomize changes no other field.
  • Editing a pick entry's own text never changes its id.
  • Any card type may join any other card type. No pair is refused. A Beat joined straight to a Chapter is accepted and keeps the role the user chose.
  • Expand Into A Canvas creates a canvas and places the same item on it. Editing the card on either canvas changes both.
  • Deleting a canvas clears detail_canvas_id on every card that pointed at it.
  • A cycle between two detail canvases is created, saved, reopened and navigated without a crash.
  • Deleting the last placement of a Character keeps the Character. It appears in the Unplaced list. Deleting it from there removes it, and undo brings it back whole.
  • Search finds a blueprint card by its name and by text inside a Long Text field.
  • Turning Show Writing Cards off removes the Writing heading and its seven entries from the Add menu, and turning it on restores them.
  • With the toggle off, a writing card already on a canvas still draws, still edits, still connects and is still found by search.
  • A settings.json written before P6, with no show_writing_cards key, reads as on. The Add menu is not emptied.

Proves the old behaviour still works

  • The delete rule for the four original kinds is unchanged. Deleting the last placement of an image still deletes the item and its picture file, and undo still brings both back. This is the regression that matters most, because section 5 changes the rule beside it.
  • Search still ranks canvas names first.
  • Note, image, link and video cards render and edit exactly as before.
  • Existing connections still draw, still carry their labels, and still follow and leave with their cards.
  • A network monitor records zero traffic for a whole session that creates every card type, runs Randomize and fills every list field.
  • A Long Text field can never run script. The existing sanitised Markdown path is proved against the new field.
  • Every screen renders correctly in the dark theme, at the locked token values.
  • Every new control is reachable and operable from the keyboard alone.
  • The installer stays under 20 MB. The shipped lists are the first bulk data the application has ever carried, so this must be measured, not assumed.

The gate

60 frames per second while panning 250 blueprint cards carrying chips. This is the same hard gate P1 set and every phase since has re-measured. Chips add elements to every card face. This is the first feature that makes a card face more expensive, so the gate is the real risk, not a formality.

10. Build plan

This is phase P6. No existing phase is renumbered. The order below puts the riskiest assumption first.

  1. Migration 0007 — rebuild item with the widened kind CHECK. Prove it against a project holding all four existing kinds. This is first because it rewrites a table holding the user's work, and everything else waits on it.
  2. Migrations 0008 and 0009 — the connection role column and the per-project user list table.
  3. The blueprint and field types, in src/lib/, mirrored on the Rust side. The blueprint reader and the seven shipped card type files.

  5. The blueprint item payload, and the item commands that read and write a field.
  6. The corrected delete rule, and the Unplaced list. Do this before the card is drawn. It is the item most likely to force a rethink, because it changes a shipped rule.
  7. The generated properties panel — one control per field kind, in blueprint order, with the meaning line as help text.
  8. The combo control, the pick entry shape, and the per-project user list.
  9. One-hop list filtering, as a pure function, tested on its own.
  10. The Scale control, the shaped roll, the guarantee, and undo.
  11. The blueprint card face — text fields and chips, generated from show_on_face.

Riskiest assumption first. Two tasks carry nearly all the risk. Migration 0007 is a rewrite of a table holding real user work. The corrected delete rule changes a rule that has shipped and that four card kinds still depend on. Both are near the front on purpose.
