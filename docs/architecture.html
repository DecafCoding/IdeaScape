IdeaScape — Architecture

How the application gets built. The MVP plan says what gets built.

Written: 2026-09-05, from the architecture interview.
Scope authority: docs/mvp-plan.html
Market input: docs/competitive-scan.html

1. Context

This design serves the MVP in docs/mvp-plan.html. That plan holds 17 in-scope items. It was frozen on 2026-09-05 and amended on 2026-09-05 and 2026-09-06 by dev-ui-update, which added four items and removed Vimeo.

IdeaScape is a single-user Windows desktop application. The user places cards on a canvas and joins them with lines to build a concept.

Inherited constraints

  • One user. One machine. No accounts, no sharing, no cloud storage. These are on the plan's "never" list.
  • 60 frames per second while panning a canvas that holds 250 cards. This is the P1 gate.
  • 25 canvases in one project. A project opens in under 2 seconds.
  • Installer under 20 MB.
  • The application makes no network call the user did not start. No usage tracking. No update check.
  • Windows 11 only.
  • Zero running cost. There is no server.
  • One project folder holds a readable SQLite file and the original picture files.

Market input used

Three market-wide signals from the competitive scan shaped decisions here.

  • Performance at scale. Slow pan and zoom is the loudest repeated complaint in the category. It drove the front-end framework choice and the culling design.
  • Data lock-in and offline use. Users choose local-first tools for this reason. It supports the local SQLite file and the self-contained project folder.
  • Search quality. Users say Milanote search returns loose notes instead of the board they asked for. The answer is ranking, not indexing. Canvas names rank first.

Open architecture inputs from the plan

The plan parked three items under "Not yet decided". All three are settled in this document.

  • The web interface framework. Settled in section 2.
  • The rich text approach for note cards. Settled in section 3.
  • The exact search method inside SQLite. Settled in section 3.

2. Stack

Desktop shell: Tauri 2 with a Rust backend

settledundo cost: expensive

The application is a Tauri 2 desktop shell. The backend is Rust. The interface is web technology, drawn in the WebView2 engine that ships with Windows 11.

This departs from the house default of C# and .NET. The reason is two hard targets in the plan. A self-contained .NET installer is about 60 to 80 MB, which breaks the 20 MB limit. A Tauri installer is about 5 MB, because it uses the browser engine already on the machine.

A native .NET interface was also considered and rejected. Rich text and web link previews both need a browser engine, so a native application would have to embed one anyway. That removes the benefit and keeps the size cost.

Rust is unfamiliar to the user. The plan already records this as a risk. The Rust side stays small on purpose. See section 5.

Front-end framework: Svelte 5

settledundo cost: expensive

Svelte 5 with runes. Runes are Svelte's fine-grained reactivity marks. A change to one card updates that card only. The other 249 cards are not touched.

React 19 was considered. It compares a tree of elements on each change. That work has to be hand-tuned to hold 60 frames per second during a drag. SolidJS was considered and is equally fast. Svelte was chosen for the larger set of canvas examples and the smaller bundle.

The build uses Vite, which Tauri 2 sets up by default. TypeScript is used throughout.

Canvas drawing: page elements with culling

settledundo cost: expensive

Carried from the MVP plan, section 6. Each card is a real element in the page. The canvas moves and scales with one CSS transform. Only the cards inside the view window are in the page. A card outside the view is removed. This is called culling.

WebGL drawing was rejected in the plan. Text editing and rich content cannot be drawn that way, so page elements would be needed on top regardless.

3. Storage

Storage engine: SQLite, one file per project

settledundo cost: expensive

Carried from the MVP plan, section 6. One project is one folder on disk.

MyProject/
  ideascape.db      SQLite. Canvases, items, placements, connections
  assets/           Every picture file, copied in, named by content hash

Pictures are copied into the folder. They are never referenced where the user left them. The folder can then be moved, zipped or backed up as one unit. A card does not break when the user moves or renames the original file.

The schema is the entity table in the MVP plan, section 4. That plan owns the data model. This document does not restate it.

Database access: rusqlite, bundled, with rusqlite_migration

settledundo cost: cheap

rusqlite with the bundled feature. SQLite is compiled into the application. There is no system library to find on the user's machine. Calls are synchronous, which suits one local file with one reader.

Bundling also guarantees that the FTS5 module is present. FTS5 is SQLite's full-text search engine. The MVP does not use it. Having it present keeps the search decision below cheap to undo.

Migrations use rusqlite_migration. Numbered SQL files live in src-tauri/migrations/. The database version is checked when a project opens.

sqlx was considered. It checks SQL at build time, but it is asynchronous. That adds work with no gain for one local file. sea-orm was considered and rejected. It hides the query plan, which matters for a later FTS5 move.

Search: plain LIKE scan, canvas names ranked first

settledundo cost: cheap

Search runs three LIKE queries. One over canvas names. One over note card titles. One over note card body text. Canvas name results are returned first, then card results.

Amended 2026-09-05 by dev-ui-update: it was two queries. The note payload gained a title field, so the title is searched as well as the body. A card hit on either field is one result, named by its title.

The size limits make this fast enough. 25 canvases times 250 cards is about 6,000 rows at most. A full scan of 6,000 short rows takes a few milliseconds.

FTS5 was considered. At this data size it buys no measurable speed. The market complaint about search is about ranking, and the ranking rule above answers it directly. Moving to FTS5 later only adds a table and three triggers. No existing table changes.

Note cards: Markdown text, plain text box while editing

settledundo cost: moderate

A note card stores Markdown in the note { text } payload the plan defines. The card shows the rendered result. When the user edits the card, it becomes a plain text box holding the Markdown source. Toolbar buttons insert Markdown marks for bold, italic and lists.

No editor library is used. TipTap, which is built on ProseMirror, was considered. One instance per card would put 250 editors on the canvas and fail the 60 fps gate. Mounting one instance only on the focused card still adds about 150 KB and changes the stored payload to HTML.

Keeping the stored value as plain Markdown also keeps the LIKE search simple. The stored text is the searched text.

Assets: copied into the project folder, named by content hash

settledundo cost: moderate

Every picture is copied into assets/ when it is added. The file name is a hash of the file content. A hash is a short fixed-length value computed from the bytes. Two identical pictures then share one file.

An asset value in an item payload is always a file name. It is never an absolute path. This is carried from the MVP plan, section 4.

The hash algorithm is not chosen. See section 11.

Settings: one JSON file per machine, outside every project

settledundo cost: cheap

Application settings live in settings.json under %APPDATA%\IdeaScape. That is one file per machine, not one per project. The Settings screen names this path in its own footer, so it is user-visible.

It holds the four values the Settings screen edits: the auto-save cadence, snap to grid, the zoom modifier, and the theme. The project folder path shown there is read-only and comes from the open project, not from this file.

It is deliberately not in the project folder. A project folder must stay portable — moved, zipped or backed up whole — and it would be wrong for a copied folder to carry another machine's theme choice. Nothing in this file is user data; losing it resets the four values to their defaults and nothing else.

SQLite was considered for these four values and rejected. It would mean a second database with its own migrations for four scalars. Windows registry keys were rejected: the plan's privacy rule favours a file the user can read and delete.

Added 2026-09-05 by dev-ui-update. The Settings screen arrived with the design handoff and needed a home. See docs/design-system.html §9.11.

4. Architecture pattern

Pattern: vertical slice in the front end, modules by kind in Rust

settledundo cost: moderate

The front end is organised by feature. One feature folder holds its Svelte components, its state and its types together.

The Rust side is organised by kind, not by feature. It is small. The plan limits it to database work and file work. Feature folders there would be near-empty.

This is a partial departure from the house default. The house default is vertical slice everywhere. The front-end half matches it. The Rust half does not.

One shared state store is named up front. The canvas is not cleanly separable by feature. Cards, connections, selection, pan and zoom all read and write the same canvas state. Hiding that inside feature folders would produce cross-feature imports. Naming it once is honest and keeps the import rule in section 5 enforceable.

Import direction rule

settledundo cost: moderate

  • A feature may import from stores/ and lib/.
  • A feature may not import from another feature.
  • stores/ and lib/ may not import from any feature.
  • Code needed by two features moves to lib/. It is not imported across.
  • On the Rust side, commands/ may use db/, assets/ and fetch/.
  • db/, assets/ and fetch/ never call commands/.

6. Boundaries

Network: all fetching happens in Rust

settledundo cost: cheap

All network code lives in src-tauri/src/fetch/. The front end never makes a network call.

  • Link previews use reqwest to get the page and scraper to read the Open Graph tags. Open Graph tags are the standard page tags that carry a title, a description and a preview picture.
  • Video metadata uses the public oEmbed address for YouTube. oEmbed is a public endpoint that returns a title and a thumbnail. It needs no key and no account. Vimeo was removed from the MVP on 2026-09-06. A Vimeo address is treated as an ordinary web link and takes the link-preview path above. Adding Vimeo back is one more oEmbed address in the same module.
  • Every fetch is cut off after 5 seconds, as the plan requires.

Fetching from the front end was rejected. The browser engine blocks most cross-origin requests, so link cards would fail often. A third-party preview service was rejected. It would send every pasted address to a server outside the user's machine. That breaks the plan's privacy rule.

Internal seam: the Tauri command boundary

settledundo cost: cheap

The front end and the Rust side meet at Tauri commands only. Every call goes through one wrapper in src/lib/. That wrapper is the single place where a Rust error becomes a front-end error.

Rust returns one error type, defined in src-tauri/src/error.rs. The front end never receives a raw Rust error string.

The front end never builds SQL. It calls named commands such as create_placement. This is why the Rust side keeps a commands/ folder rather than exposing a generic query call.

7. State and failure

Saving: write on every change, group rapid changes

settledundo cost: moderate

Carried from the MVP plan, section 7.

  • Every change is written to SQLite.
  • Rapid changes, such as dragging a card, are grouped and written when the drag ends.
  • A change that touches several rows is written in one transaction. A crash part-way leaves no half-finished state.
  • Closing the application saves the view position and zoom for each canvas.

There is no concurrency problem to solve. One user, one machine, one open project at a time. SQLite runs in WAL mode for safer writes. WAL means write-ahead log.

Undo: inverse-command stack in the front end

settledundo cost: moderate

Each user action records how to undo itself. Deleting placement 42 records a command that creates placement 42 again. The stack lives in src/features/undo/.

One command may carry several effects. This is how the plan's rule is met: undo restores a deleted item, its placement, its connections and its asset files together.

The stack holds the current session only. Closing the project clears it. Persistent history is deferred in the plan.

A snapshot stack was considered. Copying 250 cards of state on each action uses too much memory, and a drag produces many actions. SQLite savepoints were considered. They tie undo to an open transaction, which fights the automatic save above.

Failure states are normal states

settledundo cost: cheap

The failure table in the MVP plan, section 7, is the contract. Two rules follow from it.

  • A failed fetch is drawn on the card. It is never an error dialog.
  • A partial failure leaves the database consistent, because multi-row changes run in one transaction. The user loses only the action in progress.

9. Deployment

Windows NSIS installer, built locally, not signed

settledundo cost: cheap

  • Target: Windows 11, 64-bit.
  • Installer: Tauri's NSIS output, including the WebView2 bootstrapper.
  • Built on the developer machine. There is no CI service.
  • Not code signed. Windows SmartScreen shows a warning on a machine that is not the developer's. This does not matter while the user is the only user.
  • One environment. There is no staging and no production split.
  • No secrets. No API keys. Nothing the user must fill in to start. The one configuration file, settings.json (section 3), is written by the application, has working defaults, and is never required to exist.
  • No update service. This is required by the privacy rule.

GitHub Actions was considered. This folder is not a git repository yet. Code signing was considered. A certificate costs about 200 US dollars per year and is only worth it when the application is sold. Neither changes any code, so both stay cheap to add.

Where the expensive decisions are proved

Four decisions are expensive to undo. All four are exercised by phase P1 in the MVP plan, and P1 carries a hard gate of 60 frames per second with 250 cards.

That ordering is deliberate. If the gate fails, the shell, the framework and the drawing approach are all still cheap to change, because almost nothing else has been built on them.

Override warning. Two decisions depart from the house default that dev-claud-md hard-codes. That default is C# with .NET and vertical slice everywhere. runtime-shell replaces it with Tauri and Rust. architecture-pattern keeps vertical slice in the front end only.

dev-claud-md must be pointed at this file. If it runs on its default, it will write C# and .NET conventions into CLAUDE.md. Every later agent run will then inherit them.
