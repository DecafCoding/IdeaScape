Version 1.0 · Written 2026-09-06 · Sources: docs/mvp-plan.html (scope authority), docs/architecture.html (technical authority), docs/design-system.html (visual authority), docs/competitive-scan.html (market research and backlog).

This PRD cites those documents. It does not re-decide anything they settle. Where they disagree with this file, they win, and this file is stale and must be corrected.

1. Executive Summary

IdeaScape is a single-user Windows 11 desktop application for developing an idea on a canvas. The user places small pieces of an idea — notes, pictures, web links and videos — on a pan-and-zoom canvas, then draws labelled arrows between them. The lines carry meaning: they show how one piece supports another. The result is a picture of the whole concept, not just a pile of its parts.

Today those pieces live in three unconnected places: a browser bookmark list, a notes application and a folder of pictures. Nothing holds the relationship between them, so the concept only ever exists in the user's head. IdeaScape puts every piece of one idea on one surface and makes the relationships explicit and editable.

The product is deliberately local, private and offline. There are no accounts, no cloud storage, no collaboration and no telemetry. One project is one folder on disk holding a readable SQLite file and the original picture files. The application makes no network call the user did not start.

Core value proposition

A fast, private, offline canvas where the connections between ideas are first-class content — not a moodboard for collecting references, and not a whiteboard for drawing.

MVP goal statement

Ship a Windows installer under 20 MB that holds 60 frames per second while panning a canvas of 250 cards, saves every change automatically, and lets the user build a multi-canvas project of notes, images, links and YouTube videos joined by labelled arrows — with a light and a dark theme and a 14-key shortcut set.

2. Mission

Give one person a place to see a whole idea at once, on their own machine, with nothing in the way.

Core principles

  1. The user owns the layout. The application never moves a card and never chooses a position. This rules out automatic mind-map layout as the core loop.
  2. Connections carry meaning. This is a tool for developing a concept, not for collecting references. Lines are content, not decoration.
  3. Local and private by construction. No accounts, no cloud, no analytics, no update check. The only network calls are link previews and video thumbnails the user triggered.
  4. Speed is the product. Slow pan and zoom is the loudest repeated complaint in this category. 60 fps at 250 cards is a hard gate in Phase 1, not a later optimisation.
  5. Failure states are normal states. A link that will not fetch is drawn on the card with a retry button. It is never an error dialog.

3. MVP Scope

3.1 In scope — core functionality

  • Pan and zoom canvas, with free placement
  • Note cards, with a title and Markdown body text
  • Image cards, by file drop, file picker and clipboard paste
  • Web link cards, showing title, icon and preview picture
  • Video cards (YouTube only), showing title and thumbnail, opening in the browser on click
  • Connections between two cards on one canvas, with arrow direction and an optional text label
  • Move, resize, multi-select, delete and z-order for cards
  • Duplicate a card, from the element menu and from the properties panel
  • Undo and redo, for the current session
  • Projects, each holding many canvases
  • A flat list of canvases inside a project, with create, rename and delete
  • Text search over canvas names and card text, with canvas names ranked first
  • The writing pack (P6) — seven typed card types generated from data blueprints, connections that carry a role, list fields printed as chips on the card face, and a card that expands into its own canvas. See feature-writing-pack.html

3.2 In scope — technical

  • Automatic save after every change
  • Works with no internet, except for link previews and video thumbnails
  • A keyboard shortcut set — the 14 keys printed on the context menus and the search footer, rising to 20 in Phase 6 (design-system.html §11.6)

3.3 In scope — appearance and configuration

  • A Settings screen, applied as changes are made: project folder (read-only), auto-save cadence, snap to grid, zoom with, theme, and — from P6 — show writing cards
  • A light and a dark theme, chosen as Light, Dark or System

4. User Stories

There is exactly one user: the owner of the machine. There are no roles, no permissions and no second persona. "The user" below always means that person.

4.1 Primary stories

US-1 — Capture a thought without breaking flow.
As the user, I want to add a note card anywhere on the canvas with one key, so that I can record a thought before I lose it.
Example: While reading about generation spaceships, the user presses N, types "Closed-loop food supply", and keeps reading. The card is saved before they touch anything else.

US-2 — Place things where they belong.
As the user, I want to drag every card to a position I choose, so that the layout itself carries my meaning.
Example: The user drags all propulsion notes to the left half of the canvas and all life-support notes to the right. Nothing snaps them back or re-flows them.

US-3 — Show how two pieces relate.
As the user, I want to draw a labelled arrow from one card to another, so that the relationship is recorded and not just remembered.
Example: The user presses C, drags from "Closed-loop food supply" to "Crew size of 400", and labels the arrow "constrains".

US-4 — Keep a picture with its idea.
As the user, I want to drop a picture from Explorer straight onto the canvas, so that the reference lives beside the note it belongs to.
Example: The user drags a hull cross-section PNG onto the canvas. The file is copied into the project folder, so moving or renaming the original never breaks the card.

US-5 — Keep a web page as a recognisable card.
As the user, I want a pasted web address to become a card with the page title, icon and preview picture, so that I can recognise it later without opening it.
Example: The user pastes an article address. The card appears at once showing the address, then fills in the title and preview within 3 seconds — or shows a retry button if it cannot.

US-6 — Split a project into canvases.
As the user, I want one project to hold many canvases, so that I can give each chapter or theme its own surface.
Example: The story project has one canvas per chapter. Characters and themes are reused across chapters, but each chapter's arrows are its own.

US-7 — Find a canvas by name, fast.
As the user, I want to search and get the canvas I named before any loose card, so that search takes me to a place, not to noise.
Example: The user types "Chapter 3". The canvas "Chapter 3" is the first result, above every card that mentions chapter three.

US-8 — Trust that nothing is lost.
As the user, I want every change saved automatically and my view position remembered, so that closing and reopening returns me exactly where I was.
Example: The user force-closes the application mid-drag. On reopening, everything is present except that one drag, and the canvas is at the same pan and zoom.

US-9 — Undo a mistake completely.
As the user, I want undo to restore a deleted card together with its picture file and its arrows, so that one wrong keypress is never destructive.
Example: The user deletes the last card of an image item. The item and its file leave the folder. Ctrl+Z brings the card, the item, the arrows and the file back together.

US-10 — Work in the light I have.
As the user, I want to choose Light, Dark or System, so that the application matches the room and the rest of my desktop.
Example: The user sets System. Windows switches to dark at sunset and IdeaScape follows, with nothing moving on screen between the two themes.

US-11 — Give a card the fields its subject needs.
As the user, I want to add a card that already knows what a character is, so that I record a personality and a set of tropes instead of retyping the same headings on a note.
Example: The user adds a Character card, types a name, drags five sliders, and picks two tropes from a list. The card face shows the picture, the name, the one-liner and two chips. Nothing was required to save it.

US-12 — Outline a chapter by wiring it together.
As the user, I want a line between two cards to say why they are joined, so that the canvas is an outline and not only a picture.
Example: The user wires four Beat cards into a Scene card, and the Scene into a Chapter card, each line reading "Feeds". The next day they wire a Beat straight into the Chapter instead, and the application accepts it without a warning.

US-13 — Zoom in on one card without leaving the outline.
As the user, I want a card to expand into its own canvas, so that a book canvas stays readable while each chapter has room of its own.
Example: On the book canvas the user selects Chapter 7 and presses Expand Into A Canvas. A new canvas opens with the same Chapter card on it. They add beats and scenes around it and write the prose. Back on the book canvas, the card shows the summary they just typed.

4.2 Technical stories

TS-1 — Prove the speed promise before building on it.
As the developer, I want the 60 fps / 250-card gate measured at the end of Phase 1, so that the drawing approach can still be changed cheaply if it fails.

TS-2 — Keep the data model reuse-ready.
As the developer, I want a card to be a placement pointing at an item, so that reusable characters and themes can be added later without rewriting every existing canvas.

TS-3 — Keep network code in one place.
As the developer, I want all fetching inside src-tauri/src/fetch/, so that the privacy rule is enforceable by reading one folder.

5. Core Architecture & Patterns

Architecture is settled in docs/architecture.html; this section summarizes it. Every data-decision named below is settled there. This PRD records those decisions and does not revisit, soften, or add alternatives beside them.

5.1 Pattern

architecture-pattern — vertical slice in the front end, modules by kind in Rust. One front-end feature folder holds its Svelte components, its state and its types together. The Rust side is organised by kind because it is small: it does database work and file work only.

One shared state store is named up front — src/stores/canvasStore.svelte.ts. Cards, connections, selection, pan and zoom all read and write the same canvas state, so hiding it inside feature folders would produce cross-feature imports.

5.2 Module layout

module-layout — the agreed directory tree:

IdeaScape/
├── src-tauri/
│   ├── src/
│   │   ├── main.rs            app start, command registration
│   │   ├── db/                connection, migrations, schema
│   │   ├── commands/          one file per area: project, canvas, item,
│   │   │                        placement, connection, search
│   │   ├── assets/            file copy, content hash, missing-file check
│   │   ├── fetch/             link preview and video metadata
│   │   └── error.rs           one error type returned to the front end
│   └── migrations/            numbered .sql files
├── src/
│   ├── features/
│   │   ├── canvas/            pan, zoom, culling, the canvas surface
│   │   ├── cards/             the four card kinds, move, resize, z-order
│   │   ├── connections/       draw, arrow, label
│   │   ├── selection/         click, drag box, keyboard
│   │   ├── undo/              session undo and redo stack
│   │   ├── projects/          project picker
│   │   ├── canvases/          canvas list, create, rename, delete
│   │   └── search/            search box and results
│   ├── stores/
│   │   └── canvasStore.svelte.ts   the one shared canvas state
│   ├── lib/                   ipc wrapper, markdown render, shared types
│   └── app.svelte
└── docs/

5.3 Import direction rule

import-direction — enforced, not advisory:

  • A feature may import from stores/ and lib/.
  • A feature may not import from another feature.
  • stores/ and lib/ may not import from any feature.
  • Code needed by two features moves to lib/. It is not imported across.
  • On the Rust side, commands/ may use db/, assets/ and fetch/.
  • db/, assets/ and fetch/ never call commands/.

5.4 Canvas drawing

rendering-approach — page elements with culling. Each card is a real element. The canvas moves and scales with one CSS transform. Only cards inside the view window are in the page; a card outside it is removed. WebGL drawing was considered and rejected, because text editing and rich content need page elements anyway.

5.5 Internal seam

ipc-contract — the front end and Rust meet at Tauri commands only, through one wrapper in src/lib/. That wrapper is the single place a Rust error becomes a front-end error. Rust returns one error type from src-tauri/src/error.rs. The front end never builds SQL and never receives a raw Rust error string.

6. Features

Every screen listed here is drawn and measured in docs/design-system.html §8–§9. That document is the visual authority; nothing visual is restated here.

6.1 The canvas

  • Pan and zoom, with culling. Dot grid background. Zoom bar.
  • Free placement — the application never positions or moves a card on the user's behalf.
  • Per-canvas view position and zoom are saved on close and restored on open.
  • Optional snap to grid, and a configurable zoom modifier key, both from Settings.

6.2 Cards — the four kinds

KindWhat it showsHow it is created
note A title and a Markdown body, rendered. Editing swaps to a plain text box holding the Markdown source, with toolbar buttons for bold, italic and lists. N, the background context menu, or paste of plain text
image The picture, with alt text. A dashed missing-file marker if the asset is gone. I, file drop from Explorer, file picker, or clipboard paste
link Page title, favicon and preview picture. Three states: fetched, no preview data, not fetched (with Refetch). Paste of a web address (Ctrl+V)
video Video title and thumbnail. Clicking opens the video in the system browser. YouTube only. Paste of a YouTube address

Shared card behaviour across all four kinds: move, resize (50 px minimum, no maximum), multi-select by click and marquee, z-order front/back, duplicate, and delete.

6.3 Connections

  • Drawn from one card to another on the same canvas, with the C tool.
  • Arrow direction, and an optional text label shown in a chip on the line.
  • The label chip is hidden below 50 px of line length. The label is kept, not lost, and returns when the cards move apart.
  • Lines follow their cards, and are deleted with them.

6.4 Projects and canvases

  • Project picker: create a new project folder, or open an existing one.
  • A project holds many canvases in a flat list in the left column: create, rename, delete, switch.
  • Deleting a project deletes its folder, its database and every asset file.

6.5 Search

A box in the left column opens a results popover over the canvas. Three LIKE queries run: canvas names, note titles, note body text. Canvas name results are always returned first, then card results. A card matching on either title or body is one result, named by its title. ↑ ↓ move through results; Enter opens.

6.6 Save, undo and redo

  • Every change is written to SQLite. Rapid changes such as a drag are grouped and written when the drag ends.
  • A multi-row change runs in one transaction, so a crash part-way leaves no half-finished state.
  • Undo is an inverse-command stack in src/features/undo/. One command may carry several effects, which is how undo restores an item, its placement, its connections and its asset files together.
  • The stack holds the current session only. Closing the project clears it.

6.7 Settings and theme

A full page replacing the canvas. Changes apply as they are made — there is no Save and no Cancel. It holds: the project folder (read-only), auto-save cadence, snap to grid, zoom with, and theme (Light / Dark / System). It names the settings.json path in its own footer.

6.8 Keyboard

14 keys, each printed on a context menu or the search footer, so the application must honour them. Phase 6 adds six more — 2 to 7, which create a Book, Chapter, Scene, Beat, Character or Location at the pointer, printed on the left column's Cards · Writing Pack submenu. 6.9 Data model

Owned by docs/mvp-plan.html §4. Reproduced here because every feature above depends on it. 

Project
 ├── Canvas          (many per project)
 │    ├── Placement  (many per canvas) ──► Item
 │    └── Connection (many per canvas) ──► two Placements
 └── Item            (the project library; many per project)

The key decision: a card is a placement, not the content. A placement holds position and size and points at an item; the item holds the content and lives in the project library. Most items have exactly one placement. A reused item has two or more — the same record, the same code path. This costs one extra table now and saves a full data-model rewrite when reusable characters and themes arrive.

note   { title, text }

An asset value is always a file name inside the project's assets/ folder. It is never an absolute path.

Ownership and lifecycle:

  • Deleting a project deletes its folder, its database and every asset file.
  • Deleting a canvas deletes its placements and connections; items are then checked against the rule below.
  • Deleting a placement deletes the connections attached to it.
  • Deleting the last placement of a note, image, link or video item deletes the item and its asset files. This stops invisible junk, because the MVP has no library screen. Undo restores all of it together.
  • Deleting the last placement of a blueprint item keeps the item. It moves to the Unplaced list in the left column, where it can be placed again or deleted for good. 8. Security & Configuration

Deployment target, environments, secrets and security posture are owned by docs/architecture.html §8 and §9. Summarized here.

8.1 Authentication and authorization

None, by design. There is one user on one machine. Accounts and sign-in are on the permanent "never" list. File-system permissions are the only access control, and they are the operating system's job.

8.2 Configuration management

  • One configuration file: %APPDATA%\IdeaScape\settings.json, holding auto-save cadence, snap to grid, zoom modifier, theme and font.
  • It is written by the application, has working defaults, and is never required to exist. Deleting it resets those five values and nothing else. It holds no user data.
  • No environment variables, and no key the application ships with. Nothing the user must fill in to start.
  • A user-supplied API key is allowed — for example a YouTube data key, or an AI key as noted in section 13. It would be held in this same file and used only for a call the user started. None is used in the MVP. The absolute rule is the privacy rule: no user information goes out over the network.
  • The project folder path shown in Settings is read-only and comes from the open project, not from this file.

8.3 Security scope

In scope:

  • Rendered Markdown is cleaned before it enters the page. A note card can never run script.
  • Fetched Open Graph values are treated as plain text. A page title is never inserted as markup.
  • A fetched web page is read for preview data only. It is never run as code.
  • Every fetch is cut off after 5 seconds.
  • All network code lives in src-tauri/src/fetch/. The front end makes no network call.
  • The front end never builds SQL. It calls named Tauri commands such as create_placement.

Out of scope:

  • Encryption of the project database or assets at rest
  • Code signing (a certificate costs ~$200/year and is only worth it if the application is sold; no code changes either way)
  • Multi-user isolation, sandboxing between projects, or any permission model
  • Sandboxing of the fetched page beyond "read for preview data, never execute"

8.4 Deployment

  • Target: Windows 11, 64-bit. One environment — there is no staging/production split.
  • Tauri NSIS installer, including the WebView2 bootstrapper.
  • Built on the developer machine. There is no CI service. GitHub Actions was considered; this folder is not a git repository yet.
  • Not code signed. SmartScreen warns on a machine that is not the developer's. Acceptable while the developer is the only user.
  • No update service. This is required by the privacy rule, not an omission.

9. Interface Specification

There is no HTTP API, no command line and no public interface for other programs. The only interface in the MVP is the Tauri command seam between the front end and Rust.

9.1 The Tauri command boundary

  • Every call goes through one wrapper in src/lib/.
  • Commands are grouped one file per area in src-tauri/src/commands/: project, canvas, item, placement, connection, search.
  • Rust returns one error type from src-tauri/src/error.rs. The wrapper is the single place that becomes a front-end error. The front end never sees a raw Rust error string.
  • There is no generic query command. This is why commands/ exists as a folder rather than a passthrough.

9.2 Illustrative command shape

Shape only — the exact signatures are settled during phase planning.

// src-tauri/src/commands/placement.rs
#[tauri::command]
fn create_placement(
    canvas_id: i64,
    item_id: i64,
    x: f64, y: f64,
    width: f64, height: f64,
) -> Result<Placement, AppError>

// src/lib/ipc.ts — the single wrapper
const p = await invokeSafe<Placement>('create_placement', {
  canvasId, itemId, x, y, width, height,
});

10. Success Criteria

10.1 MVP success definition

The MVP is finished when a real thinking session — building a multi-canvas project of notes, pictures, links and videos joined by labelled arrows — can be done end to end without the application being slow, losing work, or needing a workaround.

10.2 Functional acceptance checklist

Carried verbatim from docs/mvp-plan.html §10. Every line must pass.

  • Make a project. Make 3 canvases inside it
  • Put 250 mixed cards on one canvas. Panning holds 60 frames per second
  • That project opens in under 2 seconds
  • Paste a web address. A preview card fills in within 3 seconds, or shows a clear failure card with a retry button
  • Paste a YouTube address. The card shows the video title and thumbnail. Clicking it opens the video in the browser
  • Join cards with arrows. Put a label on an arrow
  • Close the application. Open it again. Everything is exactly as it was left, including the view position
  • Search a canvas name. That canvas is the first result
  • Force-close the application while editing. Nothing is lost except the action in progress
  • Delete the last card of an item. The item and its picture file are gone from the folder. Undo brings both back
  • Set the theme to Dark. Every screen renders correctly. Nothing moves between the two themes
  • Every screen matches docs/design-system.html at its locked token values, in light and in dark

10.4 User experience goals

  • Adding a card and drawing a line never require a menu — the printed shortcuts are enough.
  • No error dialog ever appears for a network failure. Failure is drawn on the card.
  • The user never loses more than the single action in progress.
  • Search takes the user to a place first, not to noise.
  • Nothing shifts position when the theme changes.

11. Implementation Phases

Ordered so the riskiest assumption — canvas speed — is proved first. Keep this section in step with mvp-plan.html §9 and the screen-to-phase map in design-system.html §16: a phase that moves in one moves in all three.

Phase 1: Canvas core

Estimate: the largest phase. It builds the shell, the design token layer, the canvas and the note card, and it carries the project's hard performance gate.

Goal: prove the 60 fps / 250-card assumption while the four expensive-to-undo decisions are all still cheap to change.

Deliverables:

  • Tauri 2 application shell and a working Windows build
  • Project folder, SQLite database (WAL mode) and the schema in §6.9
  • rusqlite_migration wired up, with numbered SQL files in src-tauri/migrations/
  • The full token layer, both palettes, and the data-theme attribute (the control that flips it is Phase 5; the tokens are here so the shell is not built twice)
  • Vendored Source Serif 4 and the 34 Phosphor glyphs, both local, with no network fetch
  • The application shell — title bar, left column, canvas with its dot grid, zoom bar, and the properties panel expanded and collapsed
  • Pan and zoom canvas, with culling
  • Note cards only, with a title and a Markdown body; the Markdown renderer chosen and its bundle cost measured
  • Move, resize (50 px minimum), multi-select, delete and z-order
  • Duplicate a card
  • Both context menus, and the empty-canvas state
  • Shortcuts: N Enter Esc Del Ctrl+D Ctrl+C Ctrl+A Ctrl+0 Ctrl+] Ctrl+[ Ctrl+Z Ctrl+Y
  • Automatic save, with rapid changes grouped and written on drag end
  • Undo and redo for the session (inverse-command stack)
  • Scrollbar styling for the left column and properties panel (open question, settles here)
  • A developer path into a project — a fixed folder or a command-line argument — until the picker lands in Phase 4

Validation:

  • Gate: 60 frames per second while panning 250 note cards. If this fails, the drawing approach is changed before any other work starts
  • Gate: the shell renders at the locked token values, in light and in dark

Culling method is an open question that settles in this phase: build the simple per-card box check first, measure it against 250 cards, and move to fixed grid buckets only if the frame rate misses.

Phase 2: Connections

Estimate: the smallest phase. It completes the core loop.

Goal: the application becomes usable for real thinking work, with notes and lines alone.

Deliverables:

  • Draw a line from one card to another (SVG overlay, arrowhead marker)
  • Arrow direction
  • Optional text label on a line, in a chip; hidden below 50 px of line length, and kept not lost
  • Lines move with their cards, and are deleted with them
  • The C shortcut, and the Connect tool's active and unavailable states
  • Design pass on the two undrawn states: a line mid-drag, and a selected connection in the properties panel

Validation:

  • Gate: the application is usable for real thinking work, with notes and lines only

Phase 3: Rich cards

Estimate: medium. It adds the three remaining card kinds and all network code.

Goal: every card kind in scope works, and every network failure is a drawn state rather than a dialog.

Deliverables:

  • Image cards, by file drop, file picker and clipboard paste; files copied into assets/, named by content hash (algorithm chosen here — BLAKE3 or SHA-256, speed over cryptographic strength)
  • The missing-file marker: dashed inset border, neutral ground, ph-image-broken
  • Web link cards with title, icon and preview picture, via reqwest + scraper in src-tauri/src/fetch/
  • All three link states: fetched, no preview data, not fetched with Refetch
  • Video cards via the YouTube oEmbed endpoint: title, thumbnail, opening in the browser on click
  • A 5-second cut-off on every fetch
  • The I and Ctrl+V shortcuts, with paste routing an address to a link or video card

Validation:

  • Gate: the speed target still holds with 250 mixed cards
  • All four fetch-related failure states render as normal UI, never as an error dialog

Phase 4: Library

Estimate: medium. It makes the application self-sufficient — no developer path left.

Goal: the user can create, open, organise and search projects without touching a file path.

Deliverables:

  • Project picker: create and open
  • The New project dialog, and the database-locked/damaged message on the picker (both currently undrawn)
  • The left column's canvas rows: create, rename (inline), delete (with confirm), switch
  • Text search over canvas names, note titles and note body text — three LIKE queries, canvas names ranked first
  • The search popover, and the ↑ ↓ and Enter keys in the results

Validation:

  • Gate: every functional acceptance line in §10.2 passes, except the two dark-theme lines

Phase 5: Settings and appearance

Goal: the user controls the five settings and the theme, and the dark theme is signed off end to end.

Validation:

  • Gate: every screen built in Phases 1–4 renders correctly in the dark theme, at the locked token values, with nothing moving between the two themes

Deliverables:

12. Future Considerations

Ranked backlog in docs/competitive-scan.html. Recorded here, not decided here.

12.1 Highest-value post-MVP work

  1. Export to an open file format. The MVP's most visible gap against the market. Every comparable application offers some export, and lock-in is a market-wide complaint. The data model and the readable project folder already make this straightforward.
  2. Video that plays inside its card. Every comparable application does this. IdeaScape shows title, thumbnail and link — a visible gap next to Milanote.
  3. A library screen. Shows every item in a project and its unplaced items. Partly met by P6, which ships an Unplaced list holding blueprint items only. The full screen is still wanted.
  4. Reusable shaped items — characters, tropes, themes — each with its own payload and editor. Built in P6 as the writing pack. The placement/item split in §6.9 was made for this, and it held: it cost one new kind and no data-model rewrite. See feature-writing-pack.html.
  5. Relationships between items, and a graph view. Different from canvas connections, which join placements. Strong for research users; effectively a second product on top of the canvas.

12.2 Cheap technical follow-ons

  • Vimeo video cards — one more oEmbed address in src-tauri/src/fetch/, one glyph, one address rule. The provider field already exists.
  • FTS5 search — adds one table and three triggers. No existing table changes. Worth it only if the data size grows past the current limits.
  • Code signing and CI — a certificate and a build setting. No code changes.
  • Persistent undo history — arrives with version history and restore.

12.3 Deliberately not pursued

  • A browser extension web clipper — the most praised single feature found in the scan, but pasting an address inside the application covers the same need more cheaply for one user.
  • A public API and third-party integrations — matters most to teams; export would cover part of the need.
  • Freehand drawing and an ink layer — common in whiteboard tools, less asked for in idea-collection tools. Would arrive as a new item kind.
  • AI assistance on the canvas — allowed by the privacy rule only as a call the user starts with their own key. That design also answers the market's metering complaint.
  • A mobile application — blocked by the Windows-only target and by the "no cloud" rule, which leaves no way to move data.

13. Risks & Mitigations

RiskEffectMitigation
Culling does not reach 60 fps with 250 cards The main promise of the product fails It is the Phase 1 gate, measured before any other work. Nothing else is built on the shell, the framework or the drawing approach until it passes, so all three are still cheap to change. Fallback path already identified: fixed grid buckets instead of a per-card box check
Rust and Tauri are unfamiliar Phase 1 takes longer than expected The Rust side is deliberately small — database, files, fetch, one error type. Most of the work is in the Svelte layer. The commands/ seam keeps the two halves independently learnable
The MVP misses two table stakes — export and in-card video The product looks weak next to Milanote if it is ever shown or sold Accepted deliberately, to prove the rest of the application first. The data is still the user's: the project folder holds a readable SQLite file and the original pictures. Both are the top two items in §12.1
Web pages block preview fetching, or give poor data Link cards look plain and the feature feels broken The failure states are designed as normal UI, not errors: the card is created at once with the address, marked not fetched, with a Refetch button. Three link states are drawn in the design system
YouTube changes its public oEmbed metadata Video cards lose title and thumbnail The card falls back to the address and still opens the browser. Only one provider is supported, so there is exactly one thing to fix, in one module
The library has no screen in the MVP Reusable items cannot be seen or managed, and orphan items would be invisible junk The lifecycle rule in §6.9 — deleting the last placement deletes the item and its assets — stops junk accumulating until the library screen exists. Undo restores all of it together. From P6 that rule covers the four original kinds only; a blueprint item survives and appears in the Unplaced list instead

WebView2 is missing on an older machine The application will not start The installer includes the WebView2 bootstrapper

13.1 Assumptions

  • The user works on one project at a time. There is no concurrency problem to solve.
  • 250 cards on one canvas is enough. The competitive scan shows other applications struggle at a few hundred, so this is already competitive.
  • Copying pictures into the project folder is acceptable disk use.
  • Windows 11 is the only target for the MVP.
  • Phase 1's developer path into a project is acceptable until the picker lands in Phase 4.
