Phase 5: Settings and appearance

The following plan should be complete, but validate documentation, codebase patterns, and task sanity before implementing. Pay special attention to naming of existing utils, types, and models — import from the right files.

Phase Description

Phase 5 is the last phase: it hands the user the four settings the application has been reading from hard-coded defaults since Phase 1, gives settings.json its real home under %APPDATA%\IdeaScape, and signs the dark theme off end to end across every screen Phases 1–4 built.

Four pieces of work, in the order PRD §11's Phase 5 deliverable list gives them:

  • The Settings page (design-system §9.11, frame 16a) — a full-screen page replacing the canvas, with five rows in three groups: the read-only project folder, Auto-save, Snap to grid, Zoom with, and Theme. Changes apply as they are made; there is no Save and no Cancel.
  • The segmented control and the toggle — the two controls the product has never had. Both are drawn in §9.11 down to the pixel and both need their hover, pressed, focus and disabled behaviour from §11.2 and §11.4.
  • The working theme switch — Light, Dark, System — persisting to settings.json and setting (or removing) data-theme on the root element. The palette and both data-theme blocks already ship from Phase 1; this phase ships the control that flips them and the file that remembers.
  • The dark theme's four unmeasured shadows and the --color-accent-2-400 contrast check — design-system §15.4's remaining open question, assigned to this phase. Signing the theme off also means walking every Phase 1–4 screen on the dark ground, which is where the phase's real risk lives: the shipped components resolve several colours through ramp tokens (--color-accent-700, --color-accent-600, --color-neutral-200, --color-neutral-300) that do not move between palettes, so they are wrong on dark today.

After this phase every feature folder the architecture named is filled, every command area in src-tauri/src/commands/ exists, and every line in PRD §10.2 passes — including the two dark-theme lines Phase 4's gate deliberately excluded.

User Stories

As the one person who uses IdeaScape
I want to choose how often my work is flushed to disk, whether cards snap to the grid, and whether the plain wheel zooms or pans
So that the canvas behaves the way my hand expects rather than the way a default decided.

As someone who works at night
I want to switch the application to the dark theme, or let it follow Windows
So that a bright grey page is not the only thing on the screen — and nothing on any screen moves, disappears or becomes unreadable when I do.

As the person whose machine this is
I want the Settings page to tell me exactly which file holds these four values
So that I can read it, copy it or delete it, and know that nothing left the machine.

Problem Statement

Three problems, all left standing by Phases 1–4.

  1. The four settings exist but cannot be changed. src/lib/settings.ts ships frozen defaults and three consumers read them — CanvasSurface.svelte:165 for the zoom modifier, CardLayer.svelte:152 for snap to grid, and PropertiesPanel.svelte:214/:332 for the auto-save footer copy. There is no file, no screen and no way to set any of them. The left column's gear row has been drawn and disabled since Phase 1.
  2. The theme cannot be switched. src/lib/theme.css holds the whole dark palette twice — once under :root[data-theme='dark'] and once under @media (prefers-color-scheme: dark) :root:not([data-theme='light']) — and no code anywhere sets that attribute. The theme field has zero runtime consumers.
  3. The dark theme has never been looked at. Four of its shadow values are still the interim guess Phase 1 wrote against §15.4's "roughly triple the alpha" rule, one contrast pair is unmeasured, and several shipped components reach past the role tokens into the accent and neutral ramps, which do not flip. Nobody has rendered any of it, because until this phase there was no way to.

Solution Statement

The settings file follows the template recent.json already established in the same folder: a small serde struct, std::fs, a directory taken as a parameter so no test writes to the real %APPDATA%, and a missing or corrupt file that reads as defaults rather than an error. It is written atomically — temp file plus rename — because §9.11's own helper text promises exactly that. Two commands read and write it; a third reports the folder so the footer prints a true path rather than a hard-coded one.

src/lib/settings.ts becomes src/lib/settings.svelte.ts: the same accessor names, now backed by $state, loaded once at boot through the seam and written through the seam on every change. Nothing about the three existing call sites changes except the import path.

The theme applicator is four lines and no matchMedia: light and dark set data-theme, system removes it, and the browser re-evaluates the existing media query live when Windows changes. That is why the Phase 1 palette was written as two guarded blocks.

The page itself is a third branch of the root's one screen conditional, built from two new components — a segmented control and a toggle — that exist nowhere in the product yet. Four new role tokens carry the colours the ramp tokens were doing badly, and §15.4's four dark shadows are settled into the band the three drawn dark shadows actually occupy. The contrast check is computed in a unit test from the token files, so the answer is recorded rather than eyeballed, and the whole theme is then walked screen by screen in the running application.

Edge Cases

  • No settings.json at all; an empty file; a file that is not JSON; a file whose JSON is an array or a string rather than an object.
  • A file with an unknown extra key (ignored), a missing key (defaulted), and a known key holding the wrong type or an out-of-range value (that field alone falls back).
  • A settings write that fails because the folder is read-only or the disk is full — logged, the value stays applied for the session, no dialog.
  • %APPDATA% unset, so app_data_dir() takes its USERPROFILE or . fallback; the footer must print whatever it actually resolved.
  • Theme Dark while Windows is Light, and Theme Light while Windows is Dark — the two cases the :root:not([data-theme='light']) guard exists for.
  • Windows changing its theme while the application is open, with the setting on System.
  • Opening Settings with no card selected, with a card selected (the selection survives the round trip), and while a note is mid-edit.
  • Dropping a picture, pasting an address, or pressing N while the Settings page is showing — none may create a card.
  • Closing the project while Settings is open.
  • Changing the auto-save cadence while geometry is queued.
  • Changing the cadence to 1 s and dragging continuously for longer than that.
  • The Project folder row with a very long path, and with no project open.

Assumptions and decisions

This was an unattended planning run. No requirements question was put to the user; each was decided in the authority order docs/architecture.html → docs/prd.html → CLAUDE.md → the earlier phase docs' Notes → the codebase's dominant pattern → the smallest reversible option.

  • ASSUMPTION: Settings is reachable only from the left column's gear row, so only while a project is open. Authority: design-system §9.11 — "the left column stays and its gear is the active row" — and §9.1's picker, which draws no Settings control. A gear on the picker would be an invented control, and the one setting a user might want before opening a project (the theme) is also the one that follows Windows by default.
  • ASSUMPTION: The Settings page replaces the canvas, the empty state, the drop target and the properties panel, keeping the title bar and the left column. Authority: §9.11 "a full-screen page replacing the canvas"; §13.2 gives the Settings screen no panel among its reads; and §10 contract 13 collapses the panel whenever the selection is empty, which it is on a page with no cards.

Authority: §9.11 gives the grid, its gaps and its maximum width but never assigns a row to a column; document order is the smallest reversible choice and is what align-content: start was drawn for.
  • ASSUMPTION: The group headings take the section-label type from §6.2 — 10 px, uppercase, --tracking-10, opacity .45. Authority: §9.11 names the three groups and gives them no type of their own; that style is the only heading style in the document at that level, and the left column already uses it for exactly this job.

Authority: settings-storage and CLAUDE.md both say the screen names the path so the user can find the file; app_data_dir() has two documented fallbacks for a missing %APPDATA%, and a footer that printed a path the file was not at would defeat the clause. Risks carried into execution

  • The dark-theme audit changes files four shipped phases own. Eleven style lines across nine components, every one of which must be pixel-identical in the light theme afterwards. The mitigation is that each substitution's light value is literally the same colour (--color-accent-text = accent-700, --color-accent-hover = accent-600, --color-inset = neutral-300, --color-raised = neutral-200), and the whole existing front-end suite must be green before Task 11 is called done.
  • Two invoke handler lists. Three new commands, times two registrations, in one file, with a missing entry producing a silent invoke rejection in one build profile only — and this phase's failure mode is quiet, because a failed read_settings is designed to fall back to defaults without complaint. Level 5 counts each registration rather than trusting that the feature "seemed to work", the same mitigation Phases 3 and 4 used.
  • The settings.ts → settings.svelte.ts rename is a silent-failure shape. A stale import resolves to nothing at build time in some configurations and to a stale module in others. npm run check is part of Task 2's VALIDATE for exactly this reason, and Level 5 asserts the old file is gone and unreferenced.
  • Passing a $state proxy across the command seam. The structured-clone algorithm throws on a Proxy, at runtime, in the one code path — writing a setting — that this phase is about. Task 2 spreads the store on the way out and tests that the object handed to invoke is a plain one.
  • The auto-save timer is the one thing this phase adds that runs during a pan. A frame-rate regression in Task 12 that is not explained by the cull counts is almost certainly this timer firing mid-drag. It guards on pendingCount() > 0 and reuses the existing idempotent flush, but it is the first repeating timer in the product.
  • The dark theme has never been rendered. Both palettes have shipped since Phase 1 and, until this phase, nothing could set the attribute — so Task 12 is the first time any of it has been looked at. Budget for finding more than the eleven known lines, and treat anything that moves between themes as a token-layer defect rather than a component fix, because the parity test says no measurement token may be redefined.
  • Rust remains unfamiliar to the repository owner, which docs/mvp-plan.html records as a risk. This phase adds the smallest Rust surface of any phase — one module, three commands, no async, no SQL and no new crate — and every parsing decision is a pure function with its own test.
  • This is the last phase. The gate is every remaining line in PRD §10.2, so anything Phases 1–4 deferred and nobody noticed surfaces here. Task 12's walk is deliberately exhaustive for that reason, and a FAIL recorded anywhere in the session file fails the Level 4 block.
