Phase 6: The writing pack

The following plan should be complete, but validate documentation, codebase patterns, and task sanity before implementing. Pay special attention to naming of existing utils, types, and models — import from the right files.

Phase Description

Make a card know what it is. Today every card is the same shape: item.kind is one of four values and a note holds free text. A character and a chapter are stored identically, so nothing on the canvas can be shown differently, offered a list of tropes, or told that four beats belong to one scene.

This phase adds one new item kind, blueprint, and puts the card type inside the payload rather than in the schema. A card type becomes a read-only data file — a list of fields — and one generated properties-panel state, one generated card face and three full-screen sheets read that list. Seven card types ship (Book, Chapter, Scene, Beat, Character, Location, and the existing Note). Adding an eighth is a data file and no migration.

Alongside the cards, the lines between them gain a meaning: connection.role, seven suggested roles, never a rule. Search reaches the new cards. The last-placement delete rule is corrected so a reused Character survives being taken off the one canvas they appear on, and an Unplaced list keeps the old rule's promise that nothing becomes invisible junk.

Scope, deliverables and gates: docs/prd.html §11, Phase 6. The blueprint format, the field semantics, the pick-entry shape, the role vocabulary and the data model: docs/feature-writing-pack.html §5–§10 — it owns them and this plan does not re-decide them. Every colour, size, spacing and on-screen state: docs/design-system.html §9.25–§9.33, plus §8.3 (the rail's Cards group and its 206px flyout), §9.11 (the Settings row) and §9.13 (the role on the line). Read those before writing any component; do not invent a visual value.

User Stories

As a writer building a book on a canvas
I want cards that carry the fields their type needs — a Character with personality sliders, a Book with a genre and its tropes, a Chapter with its prose
So that the canvas records the work instead of only describing it.

As a writer wiring an outline together
I want the line between two cards to say what it means — this beat feeds that scene, this chapter is part of that book
So that the shape of the story is readable from the canvas without opening anything.

As a writer reusing a character across chapters
I want the character to survive being removed from one chapter's canvas
So that tidying a canvas never destroys a record I built.

As a writer who types a trope the shipped list has never heard of
I want the value accepted, saved and offered again next time
So that the application's vocabulary follows mine rather than the other way round.

As a user who does not write fiction
I want one switch that takes the writing card types out of the menu
So that the application stays the note-and-picture canvas I opened it for.

Problem Statement

The MVP shipped with four card kinds that all store free text. docs/mvp-plan.html §1 names story building as one of the two example projects the owner gave, and §4 was built for it — the item/placement split exists so a Character can sit on three chapter canvases as one record. The data model held; the card types were never built. Four separate rows on the deferred list — reusable shaped items, templates, tags and metadata, and boards nested inside a canvas — are one feature seen from four sides, and building them separately would build the same machinery four times.

Two shipped rules are in the way. item.kind carries a SQLite CHECK constraint that cannot be altered in place, so a new kind means rebuilding a table that holds the user's work. And the last-placement delete rule destroys an item the moment its last placement goes — correct for a picture used once, catastrophic for a character removed from one chapter.

Solution Statement

Rebuild item exactly once (migration 0007) to widen the kind CHECK by one value, blueprint, and put the card type in the payload from then on. Add connection.role (0008) and a per-project vocabulary table (0009), both additive.

Ship the seven card types as read-only JSON data files embedded in the Rust binary and handed to the front end through one new command. The properties panel, the card face and the three full-screen sheets each generate themselves from a field list and know only the seven field kinds — Short Text, Long Text, Pick, Pick Many, Image, Number and Scale. Pick values are the id / your text / its sources shape carried unchanged from feature-guide-library.html, so a typed value is always accepted and never loses its provenance.

Correct the delete rule to apply to the four original kinds only, and give a blueprint item that loses its last placement a home in a new Unplaced list in the left column. Suggest a connection role from the two card types, store it, draw it, and never refuse a pair. Widen search by one query. Add one settings key that hides the pack from the menu and nothing else.

Edge Cases

  • A project written before Phase 6, holding all four kinds, opening in a Phase 6 build.
  • A blueprint card saved with every field empty except the default name.
  • A Scale field with no stored key, and one storing a real 0 — indistinguishable.
  • A Number field left empty. Empty is not zero, and neither is drawn as the other.
  • A typed pick value that later matches a shipped entry's text exactly — it keeps id: null permanently.
  • The same typed value in two casings — one row, not two.
  • A pick entry whose own text the user edits — the id never changes.
  • A trope with no genre tag, under a filtered list — sorts below, is never hidden.
  • A parent field left empty, or holding a typed value with no id — the filter returns the input order unchanged.
  • Randomize when all five sliders already sit outside −1..+1, and when all five sit at 0.
  • A Beat joined straight to a Chapter; a note joined to a Character; a card joined to itself's far end on another canvas — every pair accepted, none refused.
  • A connection carrying a role and a label on a line too short for both.
  • A pre-Phase-6 connection with role = NULL beside a new one carrying a role.
  • An Image field naming a file that is not in assets/ — the marker draws, the item survives.
  • Two Image fields on different cards naming the same content hash — one file, reference counted; deleting one card keeps the file.
  • Deleting a canvas full of Characters — every Character survives and lands in the Unplaced list.
  • A cycle of detail canvases, saved, reopened and navigated.
  • Deleting a canvas that three cards point at as their detail canvas.
  • Prose containing <script>, and a note title containing one — both sanitised.
  • A search term that is a field key (prose, name) or a blueprint id (character) — must not return every card of that type.
  • A search term containing % or _ — escape_like still applies on the fourth pass.
  • A settings.json holding the five Phase 5 keys and no sixth.
  • A settings.json holding "showWritingCards": "yes" — anything that is not literally false reads as on.
  • Show Writing Cards off, with six writing cards already on the canvas.
  • The 350px minimum window width, with every field control in the 177px panel.
  • A card name and a chip long enough to need ellipsis, in the panel and on the face.
  • Every new control operated by keyboard alone, in both themes.

Assumptions and decisions

This was an unattended run. Every question below was decided here, in the authority order architecture.html → prd.html → CLAUDE.md → earlier phase docs' Notes → the codebase's dominant pattern → the smallest reversible option.

  1. Migration 0007 runs with foreign keys off. PRAGMA foreign_keys is a no-op inside a transaction and rusqlite_migration wraps each migration in one, so the pragma cannot live in the .sql file. With foreign keys on, DROP TABLE item fires placement's ON DELETE CASCADE and empties the project. db/connection.rs therefore sets the pragma off, runs migrations, sets it back on and runs PRAGMA foreign_key_check. Authority: SQLite's documented table-rebuild procedure; the codebase pattern of doing pragma work in open_project_db. Smallest reversible option — three lines in one file, and the existing foreign-key test proves the pragma came back on.
  2. Blueprints and lists are JSON data files embedded in the Rust binary, handed to the front end by list_blueprints and list_entries. The alternative — JSON imported by Vite into the front end — would need a second copy for the two questions Rust must answer (which keys are Long Text, for search; which are Image, for asset_names), and two copies of shipped data drift. One source, through the existing command seam, conforms to ipc-contract. Vite cannot reach into src-tauri/ anyway.
  3. The field control components live in src/lib/fields/, not in a feature folder. The panel (features/shell), the card face (features/cards) and the sheets (features/writing) all draw them, and import-direction forbids a feature importing another feature — shared code moves to lib/. src/lib/Icon.svelte is the existing precedent for a shared component in lib/. feature-writing-pack.html §7 anticipates this: "the blueprint reader and the field types go in src/lib/, because two features read them."
  4. splitOnMatch moves from src/features/search/highlight.ts to src/lib/highlight.ts. The combo needs the same bolded-match run as the search results, and the rule is that shared code moves to lib/ rather than being imported across features.
  5. Default card heights are authored, because no document draws one. design-system §9.27 gives every width and auto for every height, and placement.height is NOT NULL. Authored from the drawn faces: Book 300×210, Chapter 264×168, Scene 240×130, Beat 200×104, Character 220×210, Location 220×190. Same reasoning src/lib/cardKinds.ts's header already records for the note's 236×150, and §10 contract 1 forbids the application choosing a position, not a default size.
  6. Any field the card face shows is Short Text; Long Text is reserved for the fields that never reach a face. §9.27 draws Chapter's and Scene's summary and Beat's text on the face, and the same section forbids Long Text on a face. So Summary, Logline, Role, One-liner and Beat's Text are Short Text, and Synopsis, Notes, Description and Prose are Long Text. §9.33 draws Chapter's Summary as a 46px textarea on the sheet; that is a sheet layout detail over a plain string, not a second field kind.
  7. Chapter carries themes and no tropes. Settles PRD §14.4 and design-system §15.4's third open question, "Does Chapter carry tropes as well as themes?". §9.32 records the ownership as drawn — Tropes are Book and Character, Themes are Book and Chapter — and §15.4 says "today it does not". Following what is drawn is the smallest reversible option; adding tropes later is one line in chapter.json and no code.
  8. The Character card face ships as drawn — picture, name and role. Settles §15.4's fifth open question. The design system is the authority on what a face shows, the one-liner and the trope chips are named there as "the first things to add back", and adding them is a show_on_face flag in one data file with no code change. Judging it on a real canvas of ten characters is a post-phase call, not a planning one.
  9. The role/label collision rule is implemented as §9.13 authors it — role at the midpoint, label at the midpoint of the longer half, never stacked, role wins and the label is kept but not drawn when the line is too short. Settles §15.4's fourth open question, which asks only for confirmation against a real wired canvas; the Milestone 6 checkpoint is that canvas.
  10. Esc leaves a sheet, but blurs a focused text box first. Settles §15.4's sixth open question and PRD §14.4's last row. matchAction deliberately returns 'cancel' for Escape before its inText bail so a note editor can cancel, so the two-press behaviour lives in the sheet's handler and isTextEntry is exported for it. On the Chapter sheet, where almost the whole screen is a text field, the first press gets you out of the prose and the second out of the sheet.
  11. Story tropes are the plot, setting, theme and tone tropes (259); character tropes are the character and internal-conflict tropes (151). feature-writing-pack.html §5 names the first split exactly; the library's internal_conflict function has no other home and belongs with a character. Themes are seeded from the 41 theme-function tropes, so a theme carries a real permanent id and can be counted later; the deliberate overlap with story tropes is correct — a theme trope is legitimately both.
  12. The genre list is the eight sub-genre classes, and sub-genres are the 45 ratified entries. PRD §11 and feature-writing-pack.html §5 both say "45 sub-genres in 8 classes"; the library file holds 51, six of them status: "proposed". Ship the ratified 45. Genre entry ids are authored (genre.rigor …) and the class strings are mapped to them explicitly rather than slugified, so a punctuation change in the source cannot silently produce a ninth genre.
  13. Story tropes are tagged by genre by rolling their sub-genre tier appearances up to classes. feature-writing-pack.html §5 says story tropes filter by Genre, but the library tags tropes against sub-genres. Rolling up preserves the doc's stated hop; 46 of the 259 carry a tag and the rest sort below, which is exactly the "sorts and never hides" rule. Tagging more is a re-run of the extraction script and no code.
  14. Scene gains a points-of-view list, authored in the extraction script. §9.28 draws Scene's third field as "Point of view — a combo", and no shipped list covers it. Five entries — first, third limited, third omniscient, second, epistolary. A typed value is accepted as everywhere else, so the list being short costs nothing.
  15. The five Big Five sliders' end words are authored in character.json. feature-writing-pack.html §5 fixes the five dimensions, the −3..+3 range, the weights and the guarantee, and says "a plain word at each end of every slider. The words live in the blueprint" — without naming them. Authored: Conventional/Curious, Spontaneous/Disciplined, Reserved/Outgoing, Contrary/Agreeable, Steady/Volatile. One line each in a data file.
  16. The role suggestion table. feature-writing-pack.html §5's role table lists typical uses, two of which overlap (Scene→Chapter appears under both Feeds and Part Of). A suggestion must pick one, so Scene→Chapter suggests Feeds, which the table lists first, and the user changes it in one click. Character→Chapter suggests Appears In rather than Told By, because presence is the common case and point of view is the deliberate one. Every unlisted pair, and every pair involving a note, image, link or video card, suggests null — which reads as Relates To and draws nothing.
  17. A role the user types is stored as its own text and draws the neutral ph-minus glyph. §9.13 says a typed role is accepted like any other combo value, and §7.1's set is closed, so there is no glyph to give an unknown role. It still opens to a named chip on hover.
  18. role = NULL is never normalised to 'relates-to' on write. "No back-fill is needed" is the compatibility promise, and the two are indistinguishable on screen. Writing one into the other would rewrite every old row for no visible gain.
  19. The fourth search query is a LIKE prefilter plus a precise Rust filter. Which keys are Long Text is a blueprint question and SQLite cannot answer it, so the SQL matches the payload text broadly and Rust then checks the name and each Long Text value. Without the second step, searching prose would return every Chapter. The query count, the ranking and the size argument in search-method are all unchanged.
  20. The list_entry table has no id column. A user-typed value carries no id and no source permanently — that is what marks it as the user's own (feature-writing-pack.html §5). Storing a nullable id that is always null would be a column waiting to be misused by the deferred template importer.
  21. User vocabulary is deduplicated case-insensitively against the shipped entries and against itself. SQLite's default TEXT comparison is case-sensitive, so "Chosen One" and "chosen one" would otherwise become two rows. The unique index stays on the raw text and the check happens in Rust before the insert.
  22. The extraction script runs by hand and its output is committed. The Book Guides library lives outside the repository. Nothing in package.json, build.rs or tauri.conf.json may invoke it, so a clean checkout on a machine without the library still builds the installer.
  23. Sixteen glyphs are added to the closed set, not twenty-eight. §7.1 lists 61 names and src/lib/glyphs.ts holds 33; the twelve not added here — the six align icons, arrows-horizontal, crosshair, gauge, download-simple, warning, warning-circle — are drawn in mockups whose controls shipped as text and are still unused. The set stays closed at what the code actually draws, which is the property that makes it enforceable.
  24. Placing an unplaced item puts it at the centre of the current view. §10 contract 1 says the application never chooses a position for a card, but an unplaced item has no pointer position to use — the user acted on a rail row. The view centre is the smallest defensible answer and the user drags it immediately, as they do with a pasted card.
  25. The Unplaced section is not rendered at all when empty — not dimmed, not an empty state. §8.3 gives no drawn empty state for it, and feature-writing-pack.html §6 says it "is empty and hidden until a blueprint item loses its last placement".
