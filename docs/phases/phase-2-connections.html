Phase 2: Connections

The following plan should be complete, but validate documentation, codebase patterns, and task sanity before implementing. Pay special attention to naming of existing utils, types, and models — import from the right files.

Phase Description

Phase 2 completes the core loop by joining cards with lines: a connection drawn from one card to another on the same canvas, carrying an arrow direction and an optional text label, following its cards when they move and leaving with them when they are deleted. Phase 1 shipped a canvas of note cards that move, resize, stack, duplicate, delete, save and undo, but nothing joins them. When this phase lands the application is usable for real thinking work with notes and lines alone — which is precisely the phase's stated gate.

The PRD calls this the smallest phase, and the groundwork is already in place: the connection table and its index exist in 0001_initial_schema.sql, the Connection interface already sits in src/lib/types.ts, the --color-connection / --color-arrowhead tokens and the --z-connections rung already exist in the token layer, activeTool already admits 'connect', the connect action already exists in the shortcut map, and the Connect tool row and the Connect From Here menu row are already drawn in their unavailable state. Phase 2 fills in behind all of it. No migration is added.

Work items bundled here:

  • Rust connection commands, and capturing the connections a card delete removes so undo can put them back with the cards.
  • Connections in the shared canvas store, loaded with the canvas.
  • Endpoint geometry — a line ends on a card's real edge, derived from the placement rectangle, never on an assumed one.
  • The SVG overlay, the arrowhead marker, and the HTML label chip with its 50 px rule.
  • The Connect tool, the C shortcut, the Connect From Here menu row, and the mid-drag line.
  • Selecting a connection, and the properties panel's Connection state (label and direction).
  • Lines follow their cards, are deleted with them, and come back with them on undo.
  • The design pass on the two states docs/design-system.html §15.1 leaves undrawn: a line mid-drag, and a connection selected in the panel.

Problem Statement

The product's own positioning line is "a canvas where the connections between ideas are first-class content" (docs/prd.html §1). After Phase 1 the application has no connections at all. A board of unrelated boxes is a note pile, not a concept — and every one of the comparable applications in docs/competitive-scan.html joins cards with lines. Until this phase lands, the core loop the whole plan is built around is half-built and the product cannot be evaluated against its own purpose.

There are also three concrete correctness traps waiting in the existing code. First, delete_placements relies on ON DELETE CASCADE to remove attached connection rows, so it silently destroys data that undo has no record of. Second, restore_card mints a new placement id, so a naive undo would restore cards whose connections point at ids that no longer exist. Third, the culled card set is not a safe basis for drawing lines: a line between two off-screen cards can still cross the middle of the viewport. Each has to be handled deliberately.

Solution Statement

Connections are stored in the existing connection table and reached through one new command file, src-tauri/src/commands/connection.rs, mirroring placement.rs exactly — a *_for(state, …) function holding the SQL and a thin #[tauri::command] wrapper over it, so the logic is unit-testable without a Tauri runtime. The front end reaches them only through invokeSafe.

Endpoints are never stored. They are derived at render time from the two placement rectangles by clipping the centre-to-centre line to each rectangle's edge. That is what docs/design-system.html §9.13 requires ("derive them from the placement rectangle, so a card that grows never leaves a line sprouting from its middle"), and it is also why moving or resizing a card writes nothing to the connection table: the lines simply re-derive.

Drawing is one SVG overlay that is a sibling of the card layer, placed before it in DOM order and sitting on the --z-connections rung, so cards always paint over lines. It is pointer-events: none as a whole, with a wide transparent hit path per connection carrying pointer-events: stroke, so the overlay never steals a pan, a marquee or a card drag. Label chips are HTML, not SVG text, so they sit on an opaque ground.

Deleting a card now returns the connections it removed inside the existing DeleteEffect, and the undo command re-creates them against the new placement ids by way of an old-id → new-id map built while the cards are restored. That is the mechanism docs/architecture.html's undo-model describes when it says one command may carry several effects.

Integration Tests

  • Rust cascade capture — delete_placements reports every attached connection exactly once, and leaves none behind in the table.
  • Front-end composed session — extend src/features/cards/__tests__/session.test.ts (or add a sibling connectionSession.test.ts) with the Milestone 4 script: three cards, two connections, delete the middle card, undo, redo, and assert the store and the mocked invokeSafe call log at each step.
  • The full gesture — Milestone 3's checkpoint, driven through @testing-library/svelte's fireEvent pointer events.

Edge Cases

  • A card connected to itself — rejected in Rust and never offered in the UI.
  • A second connection between the same ordered pair — rejected in Rust; the front end selects the existing one rather than showing an error.
  • The reverse pair (B→A when A→B exists) — a genuinely different connection, allowed.
  • Two cards overlapping, or sharing a centre — connectionEndpoints returns null and nothing is drawn; the row still exists and reappears when they separate.
  • A line shorter than 50 px on screen — the chip is hidden, the label is kept, the panel still shows it, and it returns unchanged on zoom-in.
  • Both endpoint cards off screen with the line crossing the viewport — the line is drawn.
  • Deleting both endpoint cards at once — the connection is captured once, not twice, and undo restores it against two freshly minted placement ids.
  • Undoing a card delete when one endpoint's other card is still deleted — the connection is skipped rather than re-created against a dead id.
  • Escape mid-drag, and a pointer release on empty space — both cancel with no write.
  • The Connect tool active when the canvas drops to one card — the tool falls back to Select.
  • A label containing Markdown or HTML — rendered as text; a connection can never run script.
  • A whitespace-only label — stored as NULL, so no empty chip is ever drawn.
  • The dark theme — lines and arrowheads read from the same two tokens, which theme.css already redefines; nothing moves between themes.

Assumptions and decisions made at plan time

This was an unattended planning run. No requirements question was put to the user; each was decided in the authority order docs/architecture.html → docs/prd.html → CLAUDE.md → docs/phases/phase-1-canvas-core.html's Notes → the codebase's dominant pattern → the smallest reversible option.

ASSUMPTION: No migration is added; the existing connection table is used as shipped. Authority: CLAUDE.md — "never edit a migration that has shipped" — and src-tauri/migrations/0001_initial_schema.sql lines 42–50 already create the table with every field PRD §6.9 names, plus idx_connection_canvas and the cascading foreign keys. Level 5 asserts the migration count stays at one.

ASSUMPTION: Endpoints are derived at render time from the two placement rectangles by clipping the centre-to-centre ray to each rectangle's border, and are never stored. Authority: docs/design-system.html §9.13 — "endpoints sit on the card's real edge, not on an assumed one. Derive them from the placement rectangle, so a card that grows never leaves a line sprouting from its middle." This is also what makes "lines follow their cards" free.

ASSUMPTION: directed is a four-value integer — 0 none, 1 arrow at the to end, 2 arrow at the from end, 3 both. Authority: docs/design-system.html §9.13 says "direction comes from the arrowhead" and names orient="auto-start-reverse" specifically because it "lets one marker serve either end", which only matters if marker-start is used; the schema types the column INTEGER NOT NULL DEFAULT 1, not a boolean, and PRD §6.3 asks for "arrow direction" without constraining it. The alternative — keeping 0/1 and flipping by swapping from_placement_id and to_placement_id — was rejected because it makes auto-start-reverse dead weight and hides a user-visible change inside the identity of the row. Reversible: one enum in one file, and every existing row already reads as 1.

ASSUMPTION: Connection selection is a separate selectedConnectionId: number | null on the store, mutually exclusive with the placement selection. Authority: docs/design-system.html §13.1 declares selection Set<placementId> — placements only — and §13.2 gives the properties panel one selected thing at a time; §15.1 names "a connection selected" as a distinct panel state. There is no drawn state for a mixed card-and-connection selection, so it is not built. Smallest reversible option.

ASSUMPTION: A selected connection is drawn as a heavier (2.5 px) stroke in --color-text plus 7 × 7 px accent square handles at both endpoints; the line itself never takes the accent. Authority: this resolves an apparent conflict between two rules that both hold. §9.13 and §10 contract 7 say connection lines are neutral ink and never take the accent; §11.4 says the square corner handles are the selection signal and that nothing else in the interface has them. Putting the accent only in the handles satisfies both, and reuses a signal the user has already learned from cards. This is one of the two undrawn states the phase was asked to design (§15.1 item 2, its panel half is below).

ASSUMPTION: A line mid-drag runs from the source card's real edge to the pointer at 1.5 px in --color-connection with stroke-dasharray="4 3" and no arrowhead; over a valid target it snaps to that card's edge, goes solid and shows the arrowhead. No transition at any point. Authority: this is the other undrawn state (§15.1 item 1). Dashed-for-provisional is the language the design system already uses for the missing-asset marker (§9.4, "a dashed inset border"); the solid snap is the only affordance that tells the user the drop will land; §11.3 puts anything tracking the pointer at 0 ms. No new token is introduced.

ASSUMPTION: The properties panel's Connection state is a header, a Label group holding one full-width .input, a Direction group of four .order-buttons in a 2 × 2 grid, and a footer whose single icon button is Delete. Authority: docs/design-system.html §8.5 gives the panel's whole anatomy and every measurement; §15.1 asks only that this state be designed, not that new components be invented. Every class and value is one the panel already ships. The segmented control was rejected: it is specified for the Settings screen and belongs to Phase 5, and pulling it forward would build a P5 component early.

ASSUMPTION: The 50 px label threshold is measured in screen pixels — world line length multiplied by zoom. Authority: docs/design-system.html §9.13 says the chip "reappears the moment the cards move apart or the canvas zooms in", which is only true if zoom is part of the measurement, and its stated reason ("no room for a 10 px chip with 1px 5px padding") is a physical-space argument.

ASSUMPTION: Label chips live inside the transformed world layer and scale with the canvas. Authority: everything else on the canvas scales with the one CSS transform (rendering-approach); a counter-scaled chip would be the only element that did not, and the 50 px rule already handles the case where the chip becomes too small to read.

ASSUMPTION: Connections are culled on the line's own bounding rectangle, not on the culled card set. Authority: correctness — a line between two off-screen cards can cross the middle of the viewport, and culling on the visible card set would drop it. It reuses rectsIntersect and viewportWorldRect from src/lib/geometry.ts, so it costs one function.

ASSUMPTION: Each connection draws a 12 px transparent hit path with pointer-events: stroke beneath its visible 1.5 px stroke, and the overlay as a whole is pointer-events: none. Authority: §9.13's SVG snippet sets pointer-events: none on the <svg> and says nothing about hit testing; a 1.5 px target is not clickable, and 12 px is just under the 13 px icon size the chrome already uses. Anything wider would start swallowing card presses.

ASSUMPTION: A connection's hit path is focusable (tabindex="0", role="button", an aria-label naming both endpoints) and Enter or Space selects it. Authority: docs/design-system.html §12 — "every action has a keyboard route. The map in 11.6 is the contract" — and 11.6 contains no key for selecting a connection. Tab order is the route that satisfies the rule without inventing a shortcut the design system has not seen.

ASSUMPTION: The Connect tool is unavailable when the canvas holds fewer than two cards. Authority: docs/design-system.html §9 frame 14b, verbatim — "Undo, Redo and Connect are all at opacity .35 — there is nothing to connect" — on a canvas holding one card.

ASSUMPTION: The C shortcut and the Connect From Here menu row require exactly one selected card and are inert otherwise. Authority: the menu row is drawn on the element menu, which §9.9 says opens on a single right-clicked card ("right-clicking a card selects it first"); a multi-card source has no drawn behaviour. Smallest reversible option.

ASSUMPTION: A card may not connect to itself, and a second connection between the same ordered pair is rejected in Rust and treated in the front end by selecting the existing connection rather than showing an error. The reverse pair is a distinct connection and is allowed. Authority: nothing states either rule; failure-surfaces requires that a failure be a normal state rather than a dialog, and selecting the row the user was trying to create satisfies their intent exactly. Reversible: one guard in one SQL function.

ASSUMPTION: An empty or whitespace-only label is stored as SQL NULL. Authority: the column is nullable and the design system draws no empty chip; one representation for "no label" keeps the chip test to a single condition.

ASSUMPTION: Connection writes are discrete — they go through writeNow, never through queuePlacementUpdate. Authority: docs/architecture.html persistence-strategy groups only rapid changes such as a drag; a connection has no continuous geometry of its own, because its endpoints are derived.

ASSUMPTION: Undo restores connections by re-creating them against the new placement ids that restore_card mints, using an old-id → new-id map built during the restore; a connection with an endpoint that stays deleted is skipped. Authority: docs/architecture.html undo-model — "undo restores a deleted item, its placement, its connections and its asset files together" — combined with the existing behaviour of restore_card, which the Phase 1 Notes already record as minting a new id the undo command adopts.

ASSUMPTION: Undo commands are pushed from src/app.svelte, not from the connections feature. Authority: the codebase's dominant pattern — every Phase 1 action does this — and the import direction rule, which forbids features/connections from importing features/undo.

ASSUMPTION: The phase gate — "usable for real thinking work, with notes and lines only" — is recorded as a scripted session in scripts/phase-2-session.md, alongside a re-run of the existing performance harness over 250 cards with connections. Authority: CLAUDE.md requires the gate be measured in the running app, not in a unit test, and the Phase 1 Notes establish a recorded artefact as the only way an automated check can assert on a measurement taken by hand. Re-running the frame gate is not demanded until Phase 3, but connections are new per-frame work and nfr-targets is continuous — measuring now is cheap and de-risks Phase 3.

ASSUMPTION: docs/design-system.html is not edited by this phase. The two states designed here are recorded in these Notes and flagged in the PR body for a later dev-ui-update run to fold in. Authority: the design system states it is written by dev-ui-update from docs/handoff/, and §15.1's own framing ("each needs a design pass before the phase that builds it") assigns the pass to the phase but not the document to the phase.

ASSUMPTION: No new npm package and no new Rust crate is added. Authority: the 20 MB installer budget in nfr-targets, and PRD §14.2 which lists every external dependency the MVP is allowed. SVG and CSS cover everything this phase draws.

ASSUMPTION: No new Phosphor glyph is introduced. Authority: docs/design-system.html §7.1 declares the set closed at 34; ph-flow-arrow (Connect) and ph-trash (Delete) are both already in src/lib/glyphs.ts, and the Direction buttons carry text labels rather than arrow glyphs.

DECISION: Rendering is Milestones rather than Flat, at four substantive milestones plus the shipping milestone. Fourteen tasks over four genuine sub-layers is well past the ~6-task threshold where a flat list stops being scannable, and each checkpoint asserts something cross-task — durability across a process boundary, endpoint agreement under an arbitrary transform, a full gesture composing tool state with the seam, and undo composing across three tables — that no individual task's VALIDATE covers.

DECISION: The Rust command file (Task 1) and the DeleteEffect change (Task 2) come before any drawing, and the pure geometry module (Task 4) before the overlay (Task 5). Both orderings are deliberate: a delete that silently destroys unrecorded rows is a data bug that gets harder to find once the UI exists, and every endpoint bug the prototype had was a maths bug the design system says was corrected twice by hand.

DECISION: delete_connections returns the rows it removed rather than (), mirroring delete_placements's DeleteEffect. The undo command needs the label and direction to put the row back, and asking the front end to remember them would put the truth in two places.

DECISION: The connection maths lives in src/lib/connectionGeometry.ts rather than being appended to src/lib/geometry.ts. geometry.ts is already shared by culling, marquee and resize at 160 lines; a separate module keeps the connection maths swappable behind a signature and its tests readable, the same reasoning src/lib/culling.ts applies to visiblePlacements.

Conflicts found between documents

One apparent conflict, resolved above rather than escalated: docs/design-system.html §10 contract 7 says connection lines "never" take the accent, while §11.4 makes the 2 px accent outline and the square handles the universal selection signal. A selected connection needs a signal and cannot use the accent on its stroke. Resolved by putting the accent only in the endpoint handles and the arrowhead marker, leaving the stroke neutral ink — both rules hold as written.

No conflict was found between docs/architecture.html, docs/prd.html and docs/design-system.html on any other point this phase touches. The PRD's Phase 2 deliverable list, the design system's §16 P2 row and the architecture's module tree agree.

Two questions the design system counts as still open — the four undrawn dark shadows and the --color-accent-2-400 contrast check — are assigned to Phase 5 and do not touch this phase: connections use only --color-connection, --color-arrowhead, --color-accent, --color-text and --color-surface, all of which have measured dark values already in src/lib/theme.css.

Risks carried into execution

The overlay stealing pointer events is the single most likely way this phase breaks Phase 1. A full-size SVG over the canvas that is not pointer-events: none kills panning, marquee selection and card dragging at once, and the symptom looks like a canvas bug rather than a connections bug. Task 5's VALIDATE asserts the computed value directly for exactly this reason.

The undo id-remapping is the subtlest correctness risk. restore_card mints new placement ids, so a connection restored against the old ids either fails on the foreign key or — worse, if the ids happen to be reused — attaches to the wrong cards. Task 12's test asserts the remapping explicitly, and Milestone 4's checkpoint exercises it through the real command path.

The frame gate is not re-demanded until Phase 3, but connections add per-frame work inside the transformed layer. If the mixed-canvas measurement in Task 13 comes in under 60 fps, the ladder is: check the connection drawn/total counts first (a broken line cull makes the number meaningless), then drop label chips below the low-zoom threshold the note cards already use (LOW_ZOOM in src/lib/geometry.ts), then batch every unselected line into a single <path> with one d string instead of one element per connection. Only after all three would rendering-approach come back into question.

Rust remains unfamiliar to the repository owner, which docs/mvp-plan.html records as a risk. This phase adds four commands over one table and one field to an existing struct — deliberately the smallest Rust surface of any phase.
