Phase 3: Rich cards

The following plan should be complete, but validate documentation, codebase patterns, and task sanity before implementing. Pay special attention to naming of existing utils, types, and models — import from the right files.

Phase Description

Phase 3 adds the three remaining card kinds and every line of network code the MVP will ever have. After Phase 2 the application is usable for real thinking work with notes and lines alone; this phase makes it usable with the material a real idea is actually made of — pictures, web pages and videos.

It bundles five related pieces of work:

  • Asset storage. A picture added by file drop, file picker or clipboard paste is copied into the project's assets/ folder and named by a hash of its bytes, so two identical pictures share one file and a moved or renamed original never breaks a card (asset-storage). The hash algorithm is chosen here — docs/architecture.html §11 assigns that question to this phase.
  • Image cards, including the missing-file marker that is drawn when the named asset is not in the folder — the item, the placement and the alt text all survive.
  • The fetch layer. All network code, in src-tauri/src/fetch/ and nowhere else (network-boundary): reqwest to get a page, scraper to read its Open Graph tags, and the public YouTube oEmbed address for video metadata. Every fetch is cut off after five seconds.
  • Link cards in all three drawn states — fetched, no preview data, and not fetched with a Refetch button — and video cards showing the YouTube title and thumbnail and opening the video in the system browser on click.
  • Paste routing. Ctrl+V becomes the single entry point that decides whether the clipboard is a card, a picture, a YouTube address, a web address or plain text — and I becomes a live shortcut.

The user value is direct: the pieces of one idea stop living in three unconnected places. The technical value is that the last expensive boundary in the product — the network — is built once, in one folder, behind one wrapper, with a failure path that is drawn on the card rather than thrown in a dialog.

Problem Statement

Three of the four card kinds do not exist. A picture cannot be added at all; an address pasted onto the canvas becomes a note holding raw text. Nothing is copied into the project folder, so a project is not yet the self-contained, portable unit storage-engine promises. And the application has never made a network call, which means the four failure states the design system draws as normal UI — no internet, no preview data, a fetch slower than five seconds, a missing asset file — are all unproven. The riskiest of those is the one that is not about the network at all: an asset file missing from the folder must never delete an item and must never crash the application.

Solution Statement

Build the asset pipeline in Rust first, because a delete that destroys bytes it cannot put back is a data bug that gets harder to find once the UI exists. Content-hash naming, a reference count over item payloads, and a project-root .trash/ folder together make an asset delete reversible in exactly the way undo-model requires. Then build the image card on top of it, so the first card kind that touches the disk is proved before the first card kind that touches the network.

Build the fetch layer next as pure Rust with pure parsing functions — URL classification, Open Graph extraction and oEmbed decoding are all testable without a socket — then the two fetching cards on top. Every one of them is created before the network is consulted (contract 2): the card exists the instant the address lands, marked not fetched, and the preview fills in or fails behind it. Nothing blocks on a socket.

Finish by re-measuring the frame gate on a canvas of 250 mixed cards, because pictures and thumbnails are real decoded bitmaps and are the first per-frame work in the product that the Phase 1 measurement did not cover.

Patterns to Follow

Naming conventions. Rust modules and functions are snake_case; row structs are PascalCase and serialize with their SQL column names unchanged, so the front-end types mirror them field for field (src/lib/types.ts says so in its header). Front-end files are camelCase.ts, components PascalCase.svelte, reactive modules *.svelte.ts. Tests are named for behaviour: fn name_condition_expected() in Rust, methodName_condition_expectedResult in TypeScript.

// src-tauri/src/commands/item.rs — the existing per-kind validation seam this phase extends
pub fn validate_payload(kind: &str, payload: &str) -> AppResult<()> {
    if !KINDS.contains(&kind) {
        return Err(AppError::Invalid(format!("card kind {kind}")));
    }
    let value: serde_json::Value = serde_json::from_str(payload)?;
    if !value.is_object() {
        return Err(AppError::Invalid(String::from("a card payload must be an object")));
    }
    if kind == "note" && !value.get("title").is_some_and(|t| t.is_string()) {
        return Err(AppError::Invalid(String::from("a note payload needs a title")));
    }
    Ok(())
}
// src-tauri/src/commands/placement.rs — one card, one transaction. Mirror this for all three kinds.
pub fn create_note_card_for(...) -> AppResult<PlacementWithItem> {

// src/lib/types.ts — tolerate a malformed row rather than throwing into a render.
export function parseNotePayload(payload: string): NotePayload {
  try {
    const value = JSON.parse(payload) as Partial<NotePayload>;
    return {
      title: typeof value.title === 'string' ? value.title : '',
      text: typeof value.text === 'string' ? value.text : '',
    };
  } catch {
    return { title: '', text: '' };
  }
}

Error handling. Rust returns AppResult<T> from every command; AppError's Display string is the only thing that crosses the seam. The front end wraps every call in app.svelte's guard(), which writes the message into the shell's message strip. A fetch failure never goes through guard() at all — it is drawn on the card (contract 3, failure-surfaces).

Logging. src/lib/logger.ts in the front end, log/tracing in Rust. Never console.log, never println! — Level 5 greps for both.

Anti-patterns to avoid. No {@html} anywhere except renderMarkdown's output — a fetched page title is inserted as a text node, never as markup. An asset must leave assets/ when the last item that names it goes, and must come back when undo puts that item back. Deleting the bytes outright would make undo a lie, so a delete moves them to a project-root .trash/ folder instead.

Testing Strategy

Unit Tests

  • Rust, in-file #[cfg(test)] per module. assets::hash — the digest is stable, the name rule sanitises, dedupe is by content. assets — copy-in, status, trash/untrash round trip, the size ceiling. commands::item — validate_payload per kind, asset_names, reference_count. fetch::classify — the address table. fetch::opengraph — extraction, fallbacks, relative resolution, clean_text. fetch::oembed — URL building and response decoding.   • TypeScript, Vitest with plain expect. The three payload parsers and cardTitle; decidePaste's priority order; imageFitBox; relativeTime; assetUrl and the status cache. Integration Tests

  • Rust. Milestone 1's checkpoint test — dedupe, two cards on one asset, a reference-counted delete, a trashed file, a restored file — over a real temp project. Milestone 3's loopback timeout test, using only std::net.
  • Front end, jsdom + @testing-library/svelte. Milestone 2's two-image card-layer test (present and missing side by side). Edge Cases

  • The same picture added twice under two names — one file, two items, two placements.
  • Two image cards sharing one asset; deleting one must not trash the file.
  • Deleting an image card whose file is already missing — the trash is a no-op, the delete still succeeds, the undo still restores the row.
  • An asset name containing .. or a separator, arriving from a hand-edited payload — refused by validate_payload, never opened.
  • A payload that is malformed JSON — the parser returns an empty card, nothing throws into a render.
  • A 40 MB picture; a zero-byte file; a file with no extension; a .svg.
  • A pasted address with no scheme, with a trailing punctuation mark, wrapped in angle brackets.
  • A YouTube address that is a channel or a playlist without v — a link card.
  • A page whose og:image is relative, protocol-relative, or a data: URI.
  • A page whose title is 20,000 characters, or contains newlines, or contains a <script> tag.
  • A server that returns 200 with Content-Type: application/pdf, or that never responds, or that redirects in a loop.
  • An item deleted while its fetch is in flight; a project closed while a fetch is in flight.
  • A refetch of an address that has changed kind since the card was created.
  • Undo of a paste, then redo, then undo again — the id remapping must survive all three.
  • A dropped folder, and a drop of forty files at once.

Assumptions and decisions made at plan time

This was an unattended planning run. No requirements question was put to the user; each was decided in the authority order docs/architecture.html → docs/prd.html → CLAUDE.md → the Notes of docs/phases/phase-1-canvas-core.html and docs/phases/phase-2-connections.html → the codebase's dominant pattern → the smallest reversible option.

  • ASSUMPTION: The content hash algorithm is BLAKE3, full 64-character lowercase hex, with the asset file named <hex>.<ext>. Authority: docs/architecture.html §11 assigns this question to P3 and says "BLAKE3 and SHA-256 are both suitable. Speed matters more than cryptographic strength here" — which names BLAKE3's own reason for existing. It also keeps the hashing off the critical path for a large drop.
  • ASSUMPTION: The image payload gains one field the PRD's list does not name — source_name, the original file name, display only. Authority: docs/design-system.html §9.4 draws a human file name on the image card and in the panel's File group (assets/truss-reference.jpg), while asset-storage requires the stored name to be a content hash. The two can only both hold if the original name is kept beside the hash. The design system is the visual authority and the architecture decision is settled; adding one display-only JSON field to a payload that is already "typed per kind" changes no table, no index and no query. Reversible: one field in one interface. A clipboard picture has no original name and is called Pasted image.
  • ASSUMPTION: The PRD's image payload field list and the Phase 1 stubs in src/lib/types.ts disagree — the stubs are image { asset, caption, alt }, link { url, title, description, asset, fetched } and video { url, title, author, asset, fetched }. The PRD §6.9 shapes win and the stubs are corrected in Task 1. Authority: docs/prd.html §6.9 restates the data model docs/mvp-plan.html §4 owns, and both outrank a stub written ahead of the phase that needed it. The stubs' own comment says they "land with their cards in Phase 3", so this was expected. The one field kept from a stub is nothing; fetched becomes fetched_at, which carries the timestamp the panel's Preview fetched 2 min ago line needs.
  • ASSUMPTION: Deleting an asset moves the file to a .trash/ folder at the project root rather than deleting the bytes, and the trash is purged when a project opens. Authority: undo-model requires undo to restore "a deleted item, its placement, its connections and its asset files together", and docs/prd.html §10.2 requires that the picture file "is gone from the folder" and that undo "brings both back". Deleting the bytes makes the second impossible; holding them in the front end's undo stack puts multi-megabyte blobs in memory for a session-only stack. A trash folder outside assets/ satisfies both sentences literally. Purging on open is correct because the undo stack is session-only, so a surviving trashed file could never be restored. Reversible: two fs::rename calls in one module.
  • ASSUMPTION: An asset is trashed only when no remaining item payload names it, counted with one SELECT count(*) … WHERE payload LIKE '%"<name>"%' rather than a stored reference count. Authority: content-hash naming means two items legitimately share one file (asset-storage states the dedupe as a benefit), so a delete must be reference-aware; search-method establishes that a full scan of ~6,000 short rows is a few milliseconds at this data size, and a derived count cannot drift from the payloads the way a stored column can.
  • ASSUMPTION: Pictures reach the page through Tauri's asset protocol, enabled in tauri.conf.json with an empty static scope and granted at runtime to the open project's assets/ directory only. Authority: an <img src> cannot read a file path, and the alternative — a command returning bytes — would put 250 base64 payloads through the IPC seam against a two-second open budget and a 60 fps gate. A runtime-scoped grant is narrower than any static scope could be, since a project folder can be anywhere on disk.
  • ASSUMPTION: convertFileSrc is re-exported from src/lib/ipc.ts rather than imported where it is used. Authority: the Phase 2 Level 5 check asserts that @tauri-apps/api/core is imported nowhere but src/lib/ipc.ts, and ipc-contract names that file as the single seam. Keeping the grep a true statement is worth one re-export.
  • ASSUMPTION: Natural image dimensions are measured in the page from the decoded <img> and patched back once through a narrow update_image_dimensions command, rather than parsed in Rust. Authority: docs/prd.html §7 forbids adding a library the architecture does not name, and no image crate is named; the page has to decode the picture to draw it anyway, so the measurement is free. The card is authored at a provisional fit-box size until the first decode, which is invisible in practice because the decode lands in the same frame.
  • ASSUMPTION: A new image card is sized by scaling the picture into a 320×320 world box preserving aspect ratio, floored at MIN_CARD_SIZE; a link card is 236×236 and a video card 272×246. Authority: docs/design-system.html §9.5 and §9.6 give the drawn widths (236 for link cards, 272 for the video thumbnail at 16:9) and the band heights (126 and 153), but no document states a default card size as a rule. Phase 1's Notes already record 236×150 for notes on the same reasoning. Contract 1 forbids the application choosing a position, not a default size. Reversible: four constants in src/lib/cardKinds.ts.
  • ASSUMPTION: The five-second cut-off is one budget covering the page request, the parse and the thumbnail and favicon downloads together, rather than five seconds per request. Authority: docs/prd.html §9.3 — "Both are cut off after 5 seconds" — and contract 4, "every fetch is cut off at 5 seconds and treated as a failure", both speak of the user-visible operation, not of individual sockets. A per-request budget could take fifteen seconds for one paste, which contradicts the three-second quality target. A thumbnail that misses the budget leaves its payload field null and the card shows the drawn "no preview picture" state, which is a normal state.
  • ASSUMPTION: A network failure, a timeout or a non-2xx status returns Ok with a not-fetched preview, never Err. Authority: failure-surfaces and contract 3 — a failed fetch is drawn on the card and is never an error dialog. In this codebase an Err from a command reaches app.svelte's guard() and lands in the shell's message strip, which is the dialog behaviour by another name. No blanket From<reqwest::Error> is added to AppError for exactly this reason.
  • ASSUMPTION: reqwest is taken with default-features = false, features = ["rustls-tls", "gzip"]. Authority: nfr-targets caps the installer at 20 MB and the default feature set pulls in the native TLS stack. rustls also removes a platform dependency, which suits an unsigned local build.

Authority: address classification has to be correct about hosts, schemes and path segments, which is what a URL parser is for and what a regular expression is famously bad at; url is already in the dependency tree transitively through reqwest, so it costs nothing.

Two official first-party plugins are the smallest reversible option, and each is used by two features.

Risks carried into execution

  • The installer budget is the likeliest thing to break in this phase. reqwest with rustls and scraper with its HTML parser are the two largest crate trees the project will ever add, against a 20 MB cap that Phase 1 measured with neither of them present. Mitigations already in the plan: default-features = false on reqwest, the existing opt-level = "s" / lto / strip release profile, and no fourth dependency for image decoding or regular expressions. If the budget is still missed, the ladder is: drop the gzip feature, then replace scraper with a hand-written meta-tag scan over the response text (Open Graph tags are shallow and this is genuinely tractable), then reconsider deployment-target — which is cheap to undo and the only decision here that could give.
  • The mixed-canvas frame gate. 250 decoded bitmaps inside one transformed layer is materially more work than 250 text cards. If the measurement misses 60 fps the ladder is: check the drawn-versus-total cull counts first (a broken cull makes the number meaningless — the Level 4 check asserts the ratio for this reason), then confirm the low-zoom simplified branch is actually taken for all four kinds, then add decoding="async" and loading="lazy" to every card image, then store a downscaled copy of any thumbnail wider than the card. Only after all four does rendering-approach come back into question.
  • The asset delete is the subtlest correctness risk in the phase. A reference count that is wrong in one direction leaves orphan files accumulating in a project the MVP has no library screen to show them in; wrong in the other, it destroys a picture another card is still using. Milestone 1's checkpoint exercises both directions through the real command path, and the LIKE pattern is anchored on the surrounding quotes so a hash prefix cannot match a different name.
  • Missing capabilities are a silent failure mode. A Tauri 2 permission that is absent does not throw where the call is written — it rejects the invoke, which this codebase logs and moves past. The title bar's window buttons have been inert since Phase 1 for exactly this reason. Task 4's VALIDATE asserts the four permissions by name rather than trusting that the feature "seemed to work".
  • The five-second contract is easy to satisfy on paper and miss in practice. A ClientBuilder::timeout covers one request, not an operation that makes three. The single tokio::time::timeout wrapper is what makes the contract true, and Milestone 3's loopback test is what proves it without a network.
  • Rust remains unfamiliar to the repository owner, which docs/mvp-plan.html records as a risk. This is the largest Rust surface of any phase — two new modules, eleven new commands, the project's first async and its first crate with a TLS stack. The mitigation is the shape of the work: every parsing decision is a pure function with its own test, and the only async in the codebase is two commands that touch no database.
