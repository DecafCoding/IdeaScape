Phase Description

Phase 1 builds IdeaScape from nothing to a running Windows application in which the user can open a project folder, pan and zoom an infinite canvas, and place, edit, move, resize, select, duplicate, reorder, delete and undo note cards — all persisted to a local SQLite database. It also lands the complete visual token layer for both themes, the vendored fonts and icons, and the full application shell chrome.

This is the largest phase in the plan, and it is first because it exercises all four expensive-to-undo architecture decisions (runtime-shell, frontend-framework, rendering-approach, storage-engine) while almost nothing has been built on them. It carries the project's one hard performance gate: 60 frames per second while panning 250 note cards. If the gate fails, the drawing approach changes before any other work starts.

User Stories

US-1 — Capture a thought without breaking flow.
As the user, I want to add a note card anywhere on the canvas with one key, so that I can record a thought before I lose it.

US-2 — Arrange thinking in space.
As the user, I want to move, resize and stack cards freely, so that the layout carries meaning the text does not.

US-3 — Never lose work.
As the user, I want every change written to disk as I make it and every action undoable within the session, so that a crash or a mistake costs me at most the action in progress.

US-4 — Work at scale without lag.
As the user, I want to pan a canvas holding 250 cards at 60 frames per second, so that the tool never gets in the way of thinking.

US-5 (technical) — Prove the risky decisions early.
As the developer, I want the shell, the framework, the drawing approach and the storage engine all exercised in the first phase, so that a failed performance gate is cheap to correct.

Problem Statement

There is no code yet — the repository holds only docs/ and CLAUDE.md. Four architecture decisions are marked expensive to undo, and every one of them is unproven. The loudest complaint in the competitive scan is that canvas tools get slow: Obsidian Canvas draws every card all the time and stalls. IdeaScape's entire performance promise rests on culling, and culling has never been measured here. Until a real Tauri window pans 250 real note cards at 60 fps, every later phase is built on an assumption.

There is also no way into a project: the project picker is deliberately Phase 4, so Phase 1 must open a project some other way or it cannot be run at all.

Solution Statement

Build bottom-up in five milestones, each with a compound checkpoint, so the gate can be measured as soon as there is something to measure and every layer below it is already proven.

  1. Foundation. Scaffold the Tauri 2 + Svelte 5 + TypeScript project, establish the single IPC seam (src-tauri/src/error.rs + src/lib/ipc.ts) before any command exists, then the database module, the schema migration, and the project/canvas commands with a developer path in.
  2. Visual foundation. Land the complete token layer for both palettes, vendor the fonts and icons locally, then build the shell chrome to the locked measurements in docs/design-system.html.
  3. Canvas. One shared store (src/stores/canvasStore.svelte.ts), one CSS-transformed layer, a dot grid that scales with zoom, the zoom bar, and per-card axis-aligned box culling with pure-function unit tests.
  4. Note cards and interaction. Item and placement commands, a sanitized Markdown render path, the note card in all its states, then move/resize/z-order, selection, duplicate/copy/paste, and both context menus.
  5. Persistence, undo and the gate. Write-on-change with drag grouping and single transactions, the inverse-command undo stack, then the 250-card / 60 fps measurement and the NSIS installer size check.

Culling starts as the simple per-card box check that docs/architecture.html §11 directs, and moves to fixed grid buckets only if the measurement misses. The Markdown path is marked for parsing plus dompurify for cleaning, chosen for size and because DOMPurify is the sanitizer of record — a note card can then never run script.

Patterns to Follow

Naming conventions. Rust modules and files are snake_case; Rust types are PascalCase; Tauri commands are snake_case verbs (create_placement). Svelte components are PascalCase files; TypeScript modules are camelCase files; a module holding runes takes the .svelte.ts extension. Tests are named for behaviour: methodName_condition_expectedResult in TypeScript, fn name_condition_expected() in Rust.

Error handling. One Rust error type, one front-end translation point. A raw Rust error string never reaches the page.

// src-tauri/src/error.rs
#[derive(Debug, thiserror::Error)]
pub enum AppError {
    #[error("the project database could not be opened: {0}")]
    DatabaseOpen(String),
    #[error("database error: {0}")]
    Database(String),
    #[error("migration failed: {0}")]
    Migration(String),
    #[error("no project is open")]
    NoProject,
    #[error("{0} was not found")]
    NotFound(String),
}

impl serde::Serialize for AppError {
    fn serialize<S: serde::Serializer>(&self, s: S) -> Result<S::Ok, S::Error> {
        s.serialize_str(&self.to_string())
    }
}

pub type AppResult<T> = Result<T, AppError>;

// src/lib/ipc.ts — the single wrapper. Nothing else in the front end calls invoke().
import { invoke } from '@tauri-apps/api/core';
import { logError } from './logger';

export class IpcError extends Error {}

export async function invokeSafe<T>(
  command: string,
  args?: Record<string, unknown>,
): Promise<T> {
  try {
    return await invoke<T>(command, args);
  } catch (raw) {
    const message = typeof raw === 'string' ? raw : 'The application could not complete that action.';
    logError(`ipc ${command} failed`, raw);
    throw new IpcError(message);
  }
}

Logging. Rust logs through log/tracing; the front end logs through src/lib/logger.ts. Never println! and never a bare console.log in shipped code.

Command shape. The front end never builds SQL. Commands take scalars and return typed rows.

// src-tauri/src/commands/placement.rs
#[tauri::command]
pub fn create_placement(
    state: tauri::State<'_, AppState>,
    canvas_id: i64,
    item_id: i64,
    x: f64, y: f64,
    width: f64, height: f64,
) -> AppResult<Placement> { /* ... */ }

Import direction (enforced, not advisory). A feature may import from stores/ and lib/. A feature may never import from another feature — shared code moves to lib/. stores/ and lib/ import from no feature. In Rust, commands/ may use db/; db/ never calls commands/.

Visual values. Every colour, size, spacing and state comes from docs/design-system.html. Components reference CSS custom properties from src/lib/tokens.css; a literal hex outside that file is a defect.

UI text. Title Case for labels, buttons, headings, menu items and dialog titles. Body copy, helper text and log messages stay in sentence case.

Testing Strategy

Unit Tests

Vitest with plain expect, jsdom environment. Test the stores and pure logic, not the visual output (CLAUDE.md Testing). Named methodName_condition_expectedResult.

  • src/lib/__tests__/ — geometry (intersect, contains, screen/world round trip), culling (the full matrix in Task 10), markdown (render and sanitize), shortcuts (every mapping and the text-input suppression), ipc (error translation), tokens and assets (static assertions over the CSS)
  • src/stores/__tests__/canvasStore.test.ts — selection operations, derived values, zoom clamping
  • src/features/cards/__tests__/ — z-order, resize clamping, duplicate semantics
  • src/features/undo/__tests__/ — the undo/redo invariants
  • Rust #[cfg(test)] modules per area, using a real SQLite file in a tempfile::TempDir — the same engine that ships, so migrations and WAL behave identically. Named fn name_condition_expected().

Integration Tests

  • Rust: open → migrate → create canvas → create note card → move → delete → reopen, asserting durability across connection close (Milestone 1 and Milestone 5 checkpoints)
  • Rust: update_placements rollback — one bad row in a batch leaves every row unchanged
  • Rust: lifecycle — deleting the last placement of an item deletes the item; deleting one of two does not
  • Front end: the Milestone 4 scripted session against a mocked IPC layer, driving store and components together
  • Front end: the Milestone 2 theme-parity spec — every shell measurement identical across data-theme while the role colours change

Edge Cases

  • A project folder that does not exist yet, and one that exists but holds no database
  • A database file that is present but unreadable — a plain message names the file; the application does not crash (the picker surface for this is Phase 4)
  • A canvas with zero placements — the empty-canvas state, not a blank screen
  • Resize to exactly 50 px, and an attempt to go below it, from all four handles
  • A card being edited while the view pans it off screen — it must not be culled and must not lose text
  • Markdown containing script tags, event-handler attributes, javascript: hrefs and malformed nesting
  • A drag interrupted by the window losing focus — the flush must still happen
  • Zoom at both clamp ends, and a wheel event with the modifier both set and unset
  • Undo with an empty stack, redo after a new action, and undo of a multi-card operation
  • A window narrowed below 420 px (panel auto-collapses) and to the 350 px minimum
  • prefers-reduced-motion: reduce — the rise, the panel slide and the zoom transform all go to 0 ms
  • Right-click near the right or bottom window edge — the menu flips rather than clipping

Assumptions and decisions made at plan time

This was an unattended planning run. No requirements question was put to the user; each was decided in the authority order docs/architecture.html → docs/prd.html → CLAUDE.md → earlier phase docs' Notes → the codebase's dominant pattern → the smallest reversible option. There is no earlier phase doc, and the repository holds no code, so the last two rungs carried the choices the documents left open.

  • ASSUMPTION: The Markdown renderer is marked for parsing plus dompurify for cleaning. Authority: docs/architecture.html §11 delegates this choice to P1 with the direction "a small renderer with built-in cleaning, measure the added bundle size". No single library both parses and cleans well; marked is the smallest well-maintained parser and DOMPurify is the sanitizer of record, and together they are roughly 60 KB gzipped against a 20 MB budget. The pair sits behind src/lib/markdown.ts, so swapping either is one file.
  • ASSUMPTION: Culling is a per-card axis-aligned box check against the viewport rectangle expanded by a 200 px screen-space margin. Authority: docs/architecture.html §11 states this explicitly — build the simple box check first, measure, move to fixed grid buckets only if the frame rate misses. The margin value is the smallest reversible option: one constant.

  • The note payload is { title, text }, not the original { text }. docs/prd.html §6.9, docs/design-system.html §15.3 answer 5, and the search-method amendment in docs/architecture.html all agree on the amended shape. Use { title, text }.
  • docs/handoff/IdeaScape UI.dc.html sets font-family: Verdana on every frame. docs/design-system.html reverted that on 2026-09-05 and is the newer authority. Build in Source Serif 4; the design file is the stale copy on this point and its own README says so.
  • docs/handoff/README.md gives the Phosphor icons as an unpkg URL, and Broadsheet's styles.css pulls Source Serif 4 from Google Fonts with an @import. PRD §7.1 requires vendored local assets and the privacy rule forbids any network call the user did not start. docs/design-system.html §14 states outright that removing that @import is not optional. Vendor both locally.
  • Motion. docs/design-system.html §11.3 specifies one easing curve and nine durations; docs/handoff/README.md turn 22 specifies two curves and four durations, and the two disagree on the menu-open duration (110 vs 140 ms), the rise distance (3 vs 4 px), the panel-collapse duration (140 vs 160 ms) and the card hover shadow.   • Cursors. §11.5 puts grab/grabbing on the canvas background at rest and move on a card body with the Select tool; the handoff puts grab only under the Pan tool and grabbing on a dragged card. Risks carried into execution

  • The gate is the phase's whole reason for existing. If 250 cards will not hold 60 fps, the fallback ladder is: confirm the drawn count is actually small (a broken cull makes the number meaningless), then simplify the card's paint at low zoom, then move visiblePlacements to fixed grid buckets behind an unchanged signature. Only if all three miss does rendering-approach come back into question — and that is precisely why it is being measured now, while nothing is built on it.
  • Rust is unfamiliar to the repository owner, which docs/mvp-plan.html already records as a risk. This phase keeps the Rust surface to eleven commands over five tables and no async, which is the mitigation the architecture chose.
  • Nine text roles sit at or under 12 px in a serif face. If a role is illegible on real Windows 11 hardware at 100% and 150% scaling, raise that size and record it — never reintroduce a second font family (docs/design-system.html §15.3 answer 2).
  • The 20 MB installer budget is checked only at the very end, in Task 22. The two things most likely to break it are importing the whole Phosphor package instead of the single regular stylesheet, and importing every Fontsource subset. Both are guarded in Task 6's VALIDATE, but the budget itself is not proven until the installer exists.
