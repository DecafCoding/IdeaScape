Phase 4: Library

The following plan should be complete, but validate documentation, codebase patterns, and task sanity before implementing. Pay special attention to naming of existing utils, types, and models — import from the right files.

Phase Description

Phase 4 makes IdeaScape self-sufficient. Phases 1–3 built a canvas that only opens the one project folder a command-line argument names; this phase removes that developer path and puts the user in charge of the library instead — creating and opening projects, organising the canvases inside one, and finding anything by name or text.

Five pieces of work, in the order the PRD §11 Phase 4 deliverable list gives them:

  • The project picker (design-system §9.1, frame 19a) — what the window shows when no project is open: New project…, Open folder…, and a 2 × 2 grid of recent projects.
  • The New project dialog, and the database-locked/damaged message on the picker — both listed as undrawn in design-system §15.1 and §15.2, designed in this phase.
  • The left column's canvas rows — create, inline rename, delete with a confirm, and switch (design-system §8.3, "Canvas rows"). Inline rename and the delete confirm are also undrawn and designed here.
  • Text search over canvas names, note titles and note body text — three LIKE queries with canvas names ranked first (architecture search-method).
  • The search popover (design-system §9.8, frame 20c) and its ↑ ↓ Enter keys.

The three feature folders the architecture named up front and left empty since Phase 1 — src/features/projects/, src/features/canvases/ and src/features/search/ — are filled in here, and after this phase every folder in module-layout holds real code.

Problem Statement

Today the application can only reach the folder that dev_project_path resolves — --project <path>, or a fixed Documents\IdeaScape\Dev project fallback. There is no way to make a second project, no way to open one, and no way out of the one that is open. Inside a project, the left column lists the canvases but they are read-only: create_canvas exists in Rust and nothing calls it, the + beside the Canvases label is drawn at the unavailable opacity, and there is no rename and no delete. The search box is drawn inert with the literal word "Search" in it.

Three of the PRD's own acceptance lines cannot be attempted in that state: "Make a project. Make 3 canvases inside it", "Search a canvas name. That canvas is the first result", and "That project opens in under 2 seconds" (there is nothing to open it from). Phase 4's gate is that every functional line in PRD §10.2 passes except the two dark-theme lines, so all three must land here.

Solution Statement

Four Rust additions and three front-end features, all inside the settled decisions:

  • A recent-projects file — %APPDATA%\IdeaScape\recent.json, written by Rust, holding at most four entries of { path, name, canvas_count, card_count, opened_at }. It is deliberately not settings.json: PRD §8.2 says that file holds exactly the four values the Settings screen edits and no user data, and settings-storage's reasoning (one file per machine, outside every project folder, so a copied project carries nothing of this machine) applies unchanged to a sibling file.
  • Five project commands and three canvas commands — list_recent_projects, default_project_parent, create_project, close_project, rename_canvas, delete_canvas, restore_canvas — plus commands/search.rs, the last file in module-layout's commands/ list that does not yet exist.
  • Search as three LIKE scans in one command, ranked canvases-first, with the snippet cut in Rust and the match highlighted by splitting text into Svelte text nodes — never by inserting markup (PRD §8.3).
  • Composition through the root. LeftColumn lives in features/shell/ and may not import features/canvases/ or features/search/. It gains two snippet props instead, and app.svelte — the one module allowed to reach into several features — fills them, exactly as it already composes CardLayer and ConnectionLayer into CanvasSurface.

The developer path goes. dev_project_path is deleted; the only survivor is a debug-only perf_gate_project_path read when --perf-gate is passed, because the frame gate has to keep being measurable in Phases 4 and 5. A release build has exactly one route into a project: the picker.

Patterns to Follow

Naming conventions. Rust: an inner *_for(state, …) function that the tests call, and a thin #[tauri::command] wrapper that only unwraps tauri::State. Commands are snake_case; the front end passes camelCase argument names and Tauri maps them.

// src-tauri/src/commands/canvas.rs — the shape every new command copies
pub fn rename_canvas_for(state: &AppState, canvas_id: i64, name: String) -> AppResult<Canvas> {
    state.with_db(|conn| {
        conn.execute(
            "UPDATE canvas SET name = ?2, updated_at = ?3 WHERE id = ?1",
            rusqlite::params![canvas_id, name, now_iso8601()],
        )?;
        Ok(conn.query_row("SELECT * FROM canvas WHERE id = ?1", [canvas_id], row_to_canvas)?)
    })
}

#[tauri::command]
pub fn rename_canvas(
    state: tauri::State<'_, AppState>,
    canvas_id: i64,
    name: String,
) -> AppResult<Canvas> {
    rename_canvas_for(&state, canvas_id, name)
}

Error handling. One error type, one wrapper, and failure drawn in the page. guard() in app.svelte puts an IpcError message into the shell's strip; the picker gets its own strip for the same reason (failure-surfaces: never a dialog).

// src/app.svelte — the existing guard, reused unchanged
async function guard(work: () => Promise<void>) {
  try {
    await work();
    errorMessage = null;
  } catch (error) {
    errorMessage = error instanceof IpcError ? error.message : 'Something went wrong.';
    logError('an action failed', error);
  }
}

Testing Strategy

Unit Tests

  • Rust, in-file #[cfg(test)] per area. Pure functions first — escape_like, snippet, the recents list mutation — then data tests against a real SQLite file in a tempfile::tempdir(), which is the same engine that ships so migrations and WAL behave identically. The recents functions take their directory as a parameter precisely so no test writes to the real %APPDATA%.
  • TypeScript, Vitest with plain expect. Stores and pure logic: splitOnMatch, the search state machine's staleness and highlight movement, the canvas-name generator, and every new undo command's undo/redo pair against a mocked invokeSafe. Not the visual output.

Integration Tests

  • The five milestone checkpoints. Each is a real test file, not a manual step: the Rust lifecycle test (M1), the session-shape component test (M2), the canvas lifecycle test (M3), the ranking and open test (M4), and the recorded-artefact assertions (M5).
  • Component tests render through @testing-library/svelte with vi.mock('../../../lib/ipc'), the idiom every existing shell and card test uses.

Edge Cases

  • A recents entry whose folder has been moved, renamed, or is on a disconnected drive.
  • A project database that is locked by another process, or is not a database at all.
  • create_project against an existing folder, a name with a path separator, a blank name, and a name that is only whitespace.
  • Deleting the only canvas in a project (refused), and deleting the active canvas (switches first).
  • Undoing a canvas delete after the project has been closed and reopened — the stack is cleared, so there is nothing to undo, which is the undo-model contract and not a bug.
  • A search query containing %, _, \, a regular-expression metacharacter, or non-ASCII text.
  • A note whose title matches and whose body also matches — one result, named by its title.
  • A card result whose canvas is not the active one.
  • A canvas renamed to a name another canvas already has (allowed; names are not unique).
  • Two projects opened in one session: the assets folder, the store, the undo stack and the recents order all have to follow.
  • A search response arriving after a newer query has been typed.

Architecture conformance

Planned entirely within docs/architecture.html. No decision is data-status="open"; the decisions this phase touches, by data-decision slug, are:

  • search-method — three plain LIKE scans (canvas names, note titles, note body text), canvas names returned first, FTS5 present and unused. Task 4 implements exactly that and no fourth query.
  • storage-engine and db-access-layer — one SQLite file per project folder, rusqlite bundled, synchronous, migrations checked when a project opens. The picker opens one project at a time; no schema change, so the migration count stays at one.
  • settings-storage — %APPDATA%\IdeaScape is the per-machine location outside every project folder. recent.json is a sibling of the Phase 5 settings.json, not part of it, so PRD §8.2's "it holds the four values the Settings screen edits" and "nothing in this file is user data" both stay literally true.
  • module-layout — commands/search.rs is the last file in the agreed commands/ list to be written, and features/projects/, features/canvases/ and features/search/ are the last three named front-end folders to be filled.
  • import-direction — enforced, not advisory. It is why LeftColumn takes snippet props instead of importing two features, and why the canvas-row context menu is raised to the root rather than importing features/shell/ContextMenu.svelte.
  • ipc-contract — eight new release commands and one debug-only one, all through invokeSafe; no generic query command; one error type; the front end builds no SQL and no file path.
  • persistence-strategy — every canvas delete and restore is one transaction, a canvas switch flushes pending geometry and the outgoing view first, and WAL is unchanged.
  • undo-model — three new inverse commands; the stack clears when the project closes and when the canvas changes, which is the scope the decision states and which nothing called before this phase.
  • failure-surfaces — the locked/damaged database, a failed create and a missing recent folder are all drawn strips on the surface the user is looking at. There is no error dialog in the phase.
  • nfr-targets — the two-second open and the 60 fps / 250-card figure are re-measured in Tasks 15 and 16, and the 20 MB installer cap is asserted in Level 4.
  • architecture-pattern — vertical slice in the front end (three new feature folders holding their own components, state and logic), modules by kind in Rust.

Doing it in Rust keeps the active canvas's store untouched, keeps the restore in one transaction, and lets the front end hand back exactly the structure the delete returned.

  • DECISION: The search box handles ↑, ↓, Enter and Esc on its own input rather than through the global dispatcher. matchAction deliberately suppresses those keys while focus is in a text box, and relaxing that rule to serve the search box would fire Delete and Enter while the user is typing into a note. The dispatcher's existing result-up and result-down actions serve the picker's Recent grid, which is not a text box.
  • DECISION: The match highlight is built by splitting text into parts and rendering <b> around the matching ones through Svelte's normal escaping, never with {@html}. PRD §8.3 forbids inserting stored or fetched text as markup, and Level 5 asserts the codebase still holds exactly one {@html}.
  • DECISION: Shared struct placement: CanvasDeleteEffect goes in src-tauri/src/db/models.rs beside DeleteEffect it mirrors; RecentProject stays in commands/project.rs because it is a file record and not a row; the search hit structs stay in commands/search.rs for the same reason. src/lib/types.ts mirrors all of them, as it already mirrors every row struct.
  • DECISION: Search reads the note title and body through json_extract rather than scanning the raw payload text. A raw scan cannot tell a title hit from a body hit, and the ranking rule needs that distinction. The first search test asserts json_extract is present in the bundled SQLite rather than assuming it.

Risks carried into execution

  • The canvas delete and its undo is the phase's real correctness risk. It is the only operation that touches all five tables at once, and it has to compose with a cascade, an orphan-item rule, a reference-counted asset trash and an id remapping. Getting it wrong in one direction leaves orphan files and rows in a project the MVP has no library screen to show them in; wrong in the other, it destroys a picture another card still uses. Milestone 1's checkpoint exercises both directions through the real command path against a real SQLite file, and Task 3's refactor exists so the rules are implemented once rather than twice.
  • The delete_placements_for refactor can break Phases 1–3 silently. Every card delete and every delete-undo in the product goes through it. The existing placement and undo tests are the regression suite; they must be green before Task 3 is called done, and no behaviour may change — only where the transaction is opened.
  • Two invoke handler lists. Eight new commands, times two registrations, in one file, with a missing entry producing a silent invoke rejection in one build profile only. Level 5 counts each registration rather than trusting that the feature "seemed to work" — the same mitigation Phase 3 used for the capability file.
  • Session state that does not follow a project switch. closeProject() and undoStack.clear() have existed since Phase 1 with no caller, the assets folder is read once at boot, and the card clipboard is a module-level array. Any one of them left behind on a switch produces a bug that looks like data corruption: another project's pictures, an undo that deletes a stranger's rows, a paste that creates cards from a project that is closed. Task 8's checkpoint opens two projects in one session for exactly this reason.
  • The search box is the first text input in the chrome. The global dispatcher's text-box rule was written for the note editor, and the interaction between it, the Esc chain and the popover is the likeliest place for a key to be swallowed or to fire twice. Handle the four keys locally and stop propagation; do not relax matchAction.
  • Rust remains unfamiliar to the repository owner, which docs/mvp-plan.html records as a risk. This phase adds one module and eight commands with no async and no new crate — a smaller and simpler Rust surface than Phase 3's — and every parsing decision (escape_like, snippet, the recents list mutation) is a pure function with its own test.
